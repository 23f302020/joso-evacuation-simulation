## 何を取得したら次へ進むか

以下の数値は性能調査の暫定的な選別基準です。PAP、研究指標、結果の採用基準ではありません。

| 段階 | 必要なデータ | 次へ進む条件・次の行動 |
|---|---|---|
| A：時間の内訳 | 同一runの計算開始/終了、validate開始/終了、record開始/終了、次startの時刻。run ID・実装/入力の一致、保留理由 | 既存3件以上で計算・検証・記録を分離できれば改善候補を順位付けする。既存ログで到達済み。欠測・中断例は別枠にする |
| B：資源の裏付け | 60秒ごとのプロセスCPU差分、private/workingメモリ、累積読書byte、全体CPU/空きメモリ/ページ読書/ディスクqueue、取得所要時間。通常セルの計算・検証・記録を少なくとも1巡 | 各処理の実行時間の95%以上を、間隔120秒以下の有効観測で覆う。PID+作成時刻を照合し、途中参加・スリープ・失敗は欠測扱い。満たせない処理は次の通常セルで補う |
| C：最初の改善選択 | A+B、上位原因の継続時間、待機の理由 | 総時間の20%以上を占める処理、または理由が確認できた5分以上の待機を優先。小さい処理の最適化から始めない。並列化が不要ならそこで候補から外す |
| D：効果確認 | 比較可能な入力/コード/PC条件の改善前後、全検証PASS、正式記録7ファイル整合、エラー/復旧回数 | まず同条件の隔離技術試験で正しさを照合し、その後の通常運用3件以上で確認。総時間中央値10%以上短縮を暫定採用目安とする。条件差が大きい場合は効果未確定。必須検証の省略で短縮した案は不採用 |

全体時間は「計算開始→正式記録終了」と「次の開始まで」の両方を示します。計算時間だけ、あるいは検証を待つ未記録件数だけで速度を評価しません。処理途中の観測だけで最終CPU時間や厳密なピークメモリを報告しません。

## 原因別の分岐

| 観測 | 次に調べること |
|---|---|
| 検証・recordが総時間の大部分 | 保存済み原本の読取計測で、CSV解凍・再計算・SHA・書込のどこが支配的か調査。現在の凍結検証器へ変更/プロファイラ注入はしない |
| 確認済みの開始待ちが長い | 誰がどの条件を待っているか特定し、既存の終了補助・通知・担当手順の不足だけ改善。排他・復旧・開始ゲートを維持 |
| 空きメモリ10%未満が5分以上続き、同時にページ出力/入出力負荷と処理速度悪化が見える | 不要アプリ削減等の前後を比較。ページ入力だけでスワップ原因と断定しない。アプリ強制終了・同期停止・増設購入は自動実施しない |
| 単一Pythonが約1論理CPUを使い続け、ディスク待ちやメモリ圧迫が小さい | CPU処理候補を保存済み成果物/隔離fixtureで測る。全体CPUの低さだけで余力ありとしない |
| ディスクqueueが継続し、CPUが低く、読書負荷と進行低下が一致 | 読書工程と同期等の競合を確認。観測削減・原本削除・無許可の出力先移設をしない |
| 通常の1本実行で上記が改善したが、独立計算に余力がある | 初めて2本並列の技術設計を検討。現CLIの1セル制約を解除せず、別途排他/保存容量/復旧/結果一致を検証する |

並列試験に進む場合も、採用基準は検証・正式記録を含む処理件数の改善です。まず同じ人工入力の逐次/2本並列でイベント・会計・距離・最終状態と独立検証の一致を確認します。時刻等の運用metadataまで同じSHAになることは要求しません。
