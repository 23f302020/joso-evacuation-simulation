## 3. 技術再登録 v6 の中身

### 3.1 分類規則の変更（`audit_native_logs`、2133–2153行の `aborts stop` の分岐だけ）
今の規則は、DRT の除去イベントと除去時刻の観測行があること、時刻が一致すること、閉鎖時刻 T について `max(0,T−0.5) ≤ 除去時刻` であること、除去理由が3種類のどれかであることを求め、さらに status が boarding か alighting であることを求める（2137–2147行）。これは**変えずに残す**。そのうえで、次の (a)〜(g) を**すべて**満たすときに限り、許容する分岐を1つ足す。

- (a) 警告の行が `Warning: Vehicle '<id>' aborts stop.` と完全に一致し、同じ車両の行は1回だけ（既存の `used` を使う）。
- (b) 同じ車両について `actor_removed`（mode=passenger）がちょうど1件ある。除去理由は `initial_or_current_closed` だけ（`route_cut`・`stranded_drt` は新しい分岐では認めない）。
- (c) 除去時刻の観測行がある（`removal_observations`、924–926行）。時刻は一致し、`observation_kind == 'parked'`、かつ `int(stop_state) & 1 == 1`。**このために、受領に `stop_state` を足す**（926行のキーに1つ追加）。
- (d) 観測行の `road_id` は外部の道路（`:` で始まらない）で、hazard に passenger の閉鎖時刻 T がある（`inf` は除く）。
- (e) `max(0, T − step) ≤ 除去時刻`（今の規則と同じ）。
- (f) **追加：** 同じ時刻に、同じ道路の `closure_applied`（mode=passenger）イベントがある。根拠は制御器のコードで、閉鎖の適用（924–937行）と、今いる道路が閉じた車両の除去（940–953行）は、同じ `now` の同じ周回で起きる。
- (g) status は条件にしない（推奨案 C。§6 J1）。対案 B は、status が {idle, pending_idle, cancel_wait} のときだけに限る。

**緩めない点：** 走行中（onroad）の除去、停車していない除去、時刻の不一致、閉鎖と無関係な除去、除去イベントがない場合、同じ警告の2回目は、すべて未分類のまま INVALID とする。`skips stop` の分岐（2133行、2144–2145行）は変えない。この分岐は、もともと status を条件にしていない。

### 3.2 fixture（人工の試験）

### 3.5 「この1件を見てから基準を変える」危険と、それを減らす設計
**危険（隠さない）：** 規則は ss261119a25 を見てから作る。その1件を通すように作った疑いは、原理的には消せない。v6 でも同じ seed なら同じ除去が再現する見込みが高く、そのとき25番目は PASS になる。さらに、検査の前提が誤っていれば、本当の異常を通す門を作ることになる。
**減らす設計：**
1. 規則の根拠を、その1件の数値ではなく、制御器のコードの経路（924–953行）に置く。時刻の幅を新たに足さない。(c)(f) は、むしろ条件を厳しくする。
2. v6 の1セル目の前に、規則・fixture・反例を文書と config に固定し（事前登録）、ユーザーの承認を得る。
3. 遡及の確認（読み取りのみ）：新旧の規則を、v5 の24セル、ss261119a25、全系列の fixture の c05〜c07（開発PCのファイルで実測すると、`aborts stop` か `skips stop` を含む fixture の log は、choice 系列で c05〜c07 だけ）に適用する。判定が変わるのが ss261119a25 だけであることを確かめる。**限界：** 24セルには DRT の除去が0件なので、新しい分岐はそこには届かない。この確認は「変わらない」ことの確認で、新しい分岐の識別力の証拠ではない。識別力の証拠は、fixture と反例が担う。
4. ss261119a25 の v5 の出力は、新しい規則でも採用しない（INVALID_PRESERVED のまま）。
5. v6 のセル1〜24について、出力の SHA（manifest を除く）を v5 の同じセルと比べる。制御器と入力が同じなら一致するはず。**一致は未確認**（registration_id などが出力に入るかは調べていない）。不一致なら止めて調べる。これは運用の停止条件で、受入の基準ではない。
6. 検査点25を足し、v6 の25番目で、新しい分岐による分類の証拠（`classified_warnings`）をユーザーが読む。

**判断（曖昧な点／選択肢／判断と理由）：**
- **J1（最も判断が割れる）：** 許容する status の範囲。A＝idle だけ／B＝{idle, pending_idle, cancel_wait}／C＝status を条件にせず、物理の証拠 (a)〜(f) で決める。**判断は C。** A は観測した1件の名札に合わせる形で、事後の当てはめの疑いが最も強い。status は制御器の周期の位相による名札で（`jdrt_realtime_choice.py`:1094–1095）、警告は SUMO の物理（停車中の除去）から出る。また、`skips stop` の分岐は、すでに status を条件にしていない。C にしないと、pickup・delivery で停車中に同じことが起きたとき、再び k セル分の流し直しが要る。反論もある：C は観測していない status まで許す。そう考えるなら B を選ぶ。決めるのはユーザー。
- **J2：** config の切り替えを、開発PCの commit と学校PCの pull で行うか、学校PCで取引スクリプトを走らせるか。**判断は前者。** 学校PCは commit しない（D-B）ので、学校PCで config を書き換えると、作業ツリーが origin とずれる。代わりに、reject と ack を pull の前に行うことを、手順の順序で固定する。
