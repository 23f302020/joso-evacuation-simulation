## 1. 親ループが1反復で呼ぶもの

### 1.1 推奨する構成

親ループは**研究CLIを直接呼ばない**。1反復につき `choice_core_sequence.py` を1回だけ呼ぶ（`--max-cells 1`）。その前後で、副作用が追記だけの読取（専用CLIの status と台帳・readback・state.json の読取）を行う。理由：start-next から readback までの全ゲートは `choice_core_sequence.py` の中に既に決定的に実装されていて（342–389）、親が同じ手順を複製すると判定が食い違うおそれがあるため。

```
[反復 k]（N = 記録済みセル数、k = N+1）
 A. 事前読取：専用CLI status（追記のみ）・台帳・前回のreadback・監視の state.json
 B. 呼び出し：choice_core_sequence.py --sequence-id <新規> --prefix <新規> \
        --expected-recorded N --max-cells 1 --prior-readback <前回のreadback JSON>
    （内部の順序：readback照合 → status → 監視 → start-next → 起動待ち → sync
      → [choice_monitor 60秒ごと + 監視の照合] → finish(check→validate→record→status)
      → readback → sync → status）
 C. 事後読取：sequence の state.json・新しいreadback・台帳・専用CLI status
 D. 判定：§2 の「進む」条件をすべて満たすときだけ k+1 へ進む。1つでも欠ければ停止する
```

## 2. 「進む」条件と「止まる」条件

### 2.1 次へ進む条件（すべて満たすこと）

1. B の終了コードが0で、標準出力と state.json が §1.2 B の値そのものである。
2. 新しいreadbackが `RECORD7_PRIMARY_READBACK_PASS` で、`recorded_cells == N+1` が台帳の行数と一致する。
3. 専用CLI status（親が別に読む）で、HOLDSがすべて空、`recorded_cells==N+1`、`next_cell` が `cfg.cells[N+1]`（N+1<70 のとき）。`core_ready`/`core_start_available` が true（次セルを開始する場合）。
4. 監視が生存していて鮮度があり、ソースSHAが一致する（A4）。
5. 次の反復の `--prefix` と `--sequence-id` がまだ使われていない（run_id は `prefix+(N+2).zfill(2)`、357行・351行。同じIDは start-next が拒否する。453–454）。

### 2.2 止まる条件

止まるときの共通動作：**親は何も再実行しない。** 停止イベントを残し、メール用のイベントを作り、終了する。run・manifest・ログ・state は**そのまま保全**する（core_sequence の docstring と、CLAUDE.md の運用規則に合わせる）。

| 1 | 状態が不明（status が失敗する、JSONが読めない、台帳が壊れている、必須キーがない） | status の終了コードが非0、または `ledger()` の RuntimeError（304）。`require_idle` は「キーが無い」ことも hold として扱う（42） | 研究状態は変わらない。人の調査待ち |

## 3. 「全70セル完了」の決定的な判定

### 3.1 判定式（専用CLIを正とする）

次の5つが**同じ時点で**すべて成り立つとき、「登録範囲の実行と記録が完了した」と判定する（研究ゴールの完了ではない。分析は別。core_sequence は常に `goal_complete:false` を返す。381, 404）。

| # | 見るもの | 条件 |
|---|---|---|
| 1 | 専用CLI `status` の JSON | `registered_cells == 70` かつ `recorded_cells == 70` かつ `next_cell == null`（411。`recorded_cells` は7ファイルが揃い、SHAが一致した行だけを数える。370–378, 395） |
| 2 | 同じ status | HOLDS 9項目がすべて `[]`（`core_start_available` は next_cell が null なので false になるのが正常） |
| 3 | 台帳 | 70行、`[row.cell_id] == cfg.cells[*].cell_id`（登録順の完全一致）、run_id は70種類とも別、全行 PASS かつ現行 registration |
| 4 | 最後のreadback | `RECORD7_PRIMARY_READBACK_PASS`、`recorded_cells == 70`、`next_cell == null`（readback 169） |
| 5 | 最後の sequence state | `COMPLETED_REGISTERED_SCOPE_PENDING_ANALYSIS`、`completed[0].run_id == 台帳の最終行の run_id` |

補足：`choice_core_sequence.py` は `count < total` を要求する（94）。このため N=70 で呼ぶと最初の検査で例外になる。親は**呼ぶ前に** §3.1 を評価して終了する。万一 start-next を直接呼んでも、`next_cell is None` なら `{"status":"ALL_RECORDED"}` を返すだけで、何も起動しない（444–445）。

### 3.2 監視の `expected_completed_targets` に何を入れるか

**結論：固定値の70は入れない。値は監視対象と基準時点から導く。しかも監視の all_complete は「完了の知らせ（要確認）」に限り、完了の判定は §3.1 の専用CLIで行う。**

根拠：

- `all_complete_evidence` が数えるのは「historical でない」かつ「`purpose != 'fixture'`」かつ status が SUCCESS の target。SUCCESS には `COMPILED_VERSION_CHECKED_NOT_SIMULATED` も含まれる（watch.py 22, 186–190）。数える範囲は、config の `patterns` に合う**すべての** manifest／build_state である（551–555）。
- 現在の config の patterns は v1〜v5 の `runs/smoke/technical` と native build の `build_state.json` を含む（`07_監視システム/config.json` を読取で確認）。`expected_completed_targets` は未設定で、設定しない限り発火しない（183–185）。
- 現在の state.json（読取で確認、2026-11-07）：targets 704、うち historical でないものは5件。内訳は native build 4件（`COMPILED_VERSION_CHECKED_NOT_SIMULATED`、purpose なし。**すでに成功として数えられる**）と core の INVALID 1件（sv26103006）。記録済みのv5 core 5件は historical。
- このため70を入れると、「native build 4件＋新しいcore 66件」でも発火する。smoke や technical suite（fixture 以外の purpose）が新しく完了すれば、さらに早く発火する。一方で、COMPLETED だが validate で不合格となり、まだ reject されていない core も成功として数えられる（INVALID になるのは reject の後。795）。

**推奨する設定（SP-07 で学校PCの config を作り直すとき）：**

1. 学校PCの `patterns` は、**現行の登録系列の core だけ**（`…/jdrt_realtime_choice_stopindex_v5/runs/*/manifest.json`）にする。smoke/technical/native build/旧系列は、別の通知に分けるか外す。
2. 監視の runtime を新しく作った時点（initial）で既にある終了済みの manifest は historical になる（watch.py 572）。このため
   **`expected_completed_targets = 登録セル数 70 − 基準時点で historical になる、現行 registration の COMPLETED core の数`**
   とする。現時点の材料では、v5 の COMPLETED core は5件（sv26103001〜05。sv26103006 は INVALID で数えない）なので **65**。ただし次の場合は、この値は成り立たない。①学校PCで再計測した時点で数が違う、②現PCの runtime state を引き継ぐ（その場合は historical の扱いが変わる）。基準を作った直後に state.json から数えた値を入れ、その数え方を記録しておく。
3. それでも監視の数は「COMPLETED の数」であり、「記録済みの数」ではない。メールの文面は「全対象完了を観測。確定は専用CLIの status で」とし、検証PASSとは書かない（SP-05 の方針どおり）。最終的な完了メールは、親ループが §3.1 を満たしたときに出すほうが決定的である（§4-D6）。

## 4. 実装前にユーザーが決める論点（研究方針の判断が要るもの）

| # | 論点 | なぜ判断が要るか | 現状のコードの挙動 |
|---|---|---|---|
| D1 | **INVALID・FAILED になったセルを、新しい run ID で自動再実行してよいか** | 同じ cell を再実行すると、事実上「不合格runを除外して取り直す」ことになる。CLAUDE.md は外れ値runの事後除外を禁じている。sv26103006 の再実行はユーザーが個別に判断した（context.md 23行） | reject（診断付き）の後は `next_cell` が同じセルのまま残り、機械的には新IDで開始できる（392–393, 411）。親は**自動で reject も再実行もしない**ことを既定にしたい。許すなら、技術的失敗（環境・中断）と検証不合格（物理・会計）を分けて規則にし、事前に登録する |
| D2 | 監視の鮮度切れなどで sequence が止まった後、**完走したcoreを親が自動で finish してよいか** | core_sequence は再開しない設計（docstring）。finish は validate/record を伴う正式採用の操作 | `unrecorded` が hold になり停止する。自動で finish するなら、「親が停止した理由が観測系だけで、core 側の異常フラグが無い」ことを条件にする案がある。要判断 |
| D3 | 監視の一時的な途切れ（再起動・120秒超）を待ってよいか、即停止か | 研究判断ではないが、無人運転の継続性と安全性のどちらを取るかの選択 | 現状は即例外（§5）。待つ実装は core_sequence の変更になり、ピン留めSHAと照合の再設計が要る |
| D4 | 途中で検証器や共通5本の不具合が見つかったときの扱い | 共通5本・resolver・bundle を変えると、READY と既存記録の同一性がすべて無効になる（realtime_choice.md 16行、status 361行）。v2→v5 と同じく**登録系列のやり直し**になり、PAP・登録の判断が要る | 親は検出したら停止するだけ（hold #5・#16） |
| D5 | 学校PCの runtime 指紋の違い（絶対パスなど）を、新しい READY で吸収してよいか。旧PCで記録した5件をそのまま70件に数えてよいか | sv26103006 は絶対パス3件の違いで INVALID になった（context.md 23行）。既存5件は status では再検証されない（status は SHA と報告の照合だけ。356–369）。系列内で実行環境が混ざることを容認するかは方法の判断 | READY は runtime 指紋と toolchain manifest に縛られている（validate.py 650–655） |
| D6 | 「全70完了」の通知を、監視の数で出すか、親の §3.1 で出すか | 誤った完了通知は研究記録の誤読につながる | 監視は数だけを見る（§3.2） |
| D7 | 70セル完了後の事前登録済み分析を、親ループの範囲に含めるか | 分析は全セルの採用後に限る（方向主張の禁止）。親は `goal_complete:false` のまま止めるのが安全 | core_sequence は分析をしない（381） |
| D8 | 逐次の順序を登録順で固定するか | 台帳は登録順の接頭辞であることを要求している（readback 105） | 順序は固定で、変更できない（変えるなら登録の変更になる） |

PAP・主要指標・比較方式・除外規則は、この親ループでは一切変えない前提とする。変える必要が出たら、親は停止してユーザーへ戻す（CLAUDE.md「作業権限と判断」）。

## 5. 無人運転で壊れやすい点

| 事象 | 何が起きるか（コード上） | 止めるべきか |
|---|---|---|
| 親ループ／core_sequence の中断（例外・強制終了） | core は `CREATE_NEW_PROCESS_GROUP` で切り離されているので動き続ける（464–466）。sequence の state は `FAILED_PRESERVED` か `RUNNING` のまま。再開機能は無い | **止める。** 再起動した親は、同じ sequence を再開せず、status の hold を見て停止を続ける |
| 監視の再起動（毎分の救済で起き直す等） | 新しいPIDになり、`monitor_identity` が変わる。鮮度が120秒を超えるか、ソースSHAが違えば、core_sequence は例外で止まる（50–55, 195–197）。**現状：稼働中の監視のソースSHA（state の `monitor_source_sha256`）はディスク上の watch.py と一致していない**（2026-11-07読取：908cff…／fde74c…）。このまま core_sequence を起動すると `observer()` で止まる | 止める（現状の設計）。学校PCでは、監視を最新のソースで起動してから系列を始めることを前提条件にする |
| サインアウト・OS再起動・Windows Update | 同じセッションのプロセスが終了し、manifest は RUNNING のまま orphan になる。writer.lock が残ることもある（54–59）。`install.ps1` は Interactive ログオンなので、ログオンするまで監視も復帰しない（導入タスク SP-08） | **止める。** `recover`（orphan）・`recover-writer`・`recover-launch` は理由を付ける人の判断（realtime_choice.md 60行）。自動復旧はしない |
| スリープ・休止 | プロセスは止まり、鮮度が切れて core_sequence は例外になる。監視は `monitoring_gap`／`stalled` を出す（watch.py 562–565） | 止める。スリープを無効にする設定を前提にする（SP-08） |
| 二重起動（親が2つ・人が手で start-next） | start-next と record は `single_writer` で排他され、`assert_idle` が running を拒否する（442–443, 683–684）。sequence_id のフォルダは `exist_ok=False`（119, 121）。ただし親どうしの排他は無い | 止める。親にも専用のロック（PIDと作成時刻付き）を設け、もう1つの親を検出したら何もせずに終わる |
| ディスク満杯 | 開始前は予約量の検査で止まる（450–451）。実行中に満杯になると core が失敗するか、出力の検証に落ちる。choice_monitor は60秒ごとに報告JSONを1つ作り、jsonlを3つ追記する（82–86）ので、長時間では小さなファイルが増える | 止める。開始前の検査は既にある。親は反復ごとに空き容量も記録する |
| 監視が target を発見できない（patterns の漏れ） | 60秒で例外（326） | 止める。学校PCの config の patterns に現行系列の runs が入っているかを、開始前に確認する |
| 長時間の calc（数時間） | `child.wait()` にタイムアウトは無い（174, finish 79）。停滞は監視の `stalled`（stale_sec=600）で通知されるだけ | 停滞の通知は止めずに知らせる。core_sequence 自身は待ち続ける |
| 表示同期の失敗（`status_progress --check` 等） | 終了コードが非0なので例外になる（229–230, 177） | 止める（記録自体は済んでいる可能性がある。readback で照合する） |
| ネットワーク断・メールの認証失効 | 研究処理には影響しない（送信器は別段。SP-03/04） | 研究は止めない。通知だけが滞る |
| 日本語パス・環境変数の欠落 | `JDRT_CHOICE_TOOLCHAIN_MANIFEST` が無いと sequence は最初の検査で止まる（109）。READY も runtime 指紋が一致しなくなる | 止める（起動前の検査で落ちるのが正常） |
| 時刻のずれ・タイムゾーン | 鮮度は `time.time()` と ISO 時刻の差で見ている（223, watch 650） | NTP 同期を前提にする。ずれは鮮度切れとして止まる |
