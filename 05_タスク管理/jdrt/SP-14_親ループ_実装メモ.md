## 2. 設計

### 2.1 1反復の流れ

```
[起動時] OSロック取得（取れなければ何もせず終了・exit 4）
         → 設定検査（不正なら exit 64、停止記録なし）
         → 未確認（ack なし）の停止が1つでもあれば何もせず終了（exit 3、新しい通知なし）
         → 前回の親が反復の途中で終わっていたら停止（PREVIOUS_PARENT_INTERRUPTED）
[反復 N→N+1]
 A. 台帳（登録順の接頭辞・run_id重複なし・全行PASS・現行registration）
    → 全70なら §3.1 の完了判定へ
    → 設定のチェックポイントに当たり、まだ ack されていなければ停止（CHECKPOINT_REACHED）
    → 前回の readback が N件を証明するか（core の require_readback を再利用）
    → 監視の state.json（120秒以内・PIDと作成時刻が一致・ソースSHAがディスクの watch.py と一致）
    → 次の run_id / sequence_id が未使用か
 B. choice_core_sequence.py --max-cells 1 を1回だけ呼ぶ（呼び出しは注入可能。既定は Popen、タイムアウト・kill・再試行なし）
 C. 終了コード0 かつ 標準出力が {"status":"COMPLETED_REGISTERED_SCOPE_PENDING_ANALYSIS","completed":1,"goal_complete":false} と完全一致
    → sequence の state.json：同じ状態・active=null・completed がこのrun 1件・cell一致・readbackの場所一致
    → 台帳が N+1 行で最後がこのrun
    → 新しい readback が N+1件を証明し、next_cell が登録上の次
    → sequence 自身が最後に取った status（state.json の command が status、exit 0）を読み、HOLDS 9項目が空・recorded=N+1・next_cell一致・（続ける場合）core_ready と core_start_available が true
 D. すべて満たしたときだけ次の反復へ。1つでも欠ければ停止
```

**親は専用CLIを一度も呼ばない。** `status` は operations.jsonl に追記するので、事後の status は core_sequence が既に保存した標準出力（`driver_logs/core_sequences/<id>/NNNN.stdout.log`）を読む。研究の状態を変える操作（start-next・finish・reject・recover 等）を呼ぶコードは親に存在しない（試験 `test_parent_never_calls_research_cli_commands`）。

### 2.2 停止（U1・D1・D2）

- 停止時、親は**何も再実行・reject・recover・finish・kill しない**（記録の `actions_taken` に明記）。子が動いていてもそのまま保全する。
- 停止記録は `<workspace>/driver_logs/parent_loop/stops/<stop_id>.json` に原子的に書き（一時ファイル→fsync→置換）、同じ内容を `parent_stop.json` に写す。中身：停止コード、補助コード（`detail_code`）、理由、根拠、時刻、反復の情報（run_id・cell_id・sequence_id・**どの段階まで済んだか**の `steps_done`）、sequence の state 要約（段階 phase、エラー、`child_may_still_be_running`、最後に走った子コマンドとログの場所、D3 の待機記録）。
- **保全が先、通知が後。** 通知（イベント書込）に失敗しても停止記録は残り、失敗内容は `stops/<stop_id>.notify.json` に残る。
- 研究の結果の数値（受入数など）は停止記録にも通知にも入れない（試験で、台帳行の値が漏れないことを確認）。
- 例外（想定外の誤り）も `INTERNAL_ERROR`、Ctrl+C は `PARENT_INTERRUPTED` として同じ手順で停止する。
- 補助コード `detail_code` は core_sequence のエラー文から機械的に付ける**参考情報**で、停止するかどうかには使わない（未知の文は `UNCLASSIFIED`）。

### 2.3 再開（ack だけ）

```
choice_parent_loop.py ack --stop-id <id> --reason "<理由>"
```

- 理由は空白だけでは受け付けない。同じ停止を二度 ack できない。ack は `stops/<id>.ack.json`（停止記録のSHA付き）を書くだけで、**何も実行しない**。
- 再実行（新しい run ID での取り直しなど）は、エラー解消後にユーザーの指示で人が行う。親には再実行の機能がない。
- run ID が既に使われていれば、親は `RUN_ID_IN_USE` で止まる。人が reject 等で処理した後に親を再起動するときは、新しい `--prefix` を渡す。
- 前回の readback が台帳と合わない（人が手で記録した等）場合は `PRIOR_READBACK_INVALID` で止まる。最新の readback を `--prior-readback` で渡す。

### 2.4 二重起動の防止

`driver_logs/parent_loop/parent.lock` に OS のバイトロック（Windows は msvcrt）。プロセスが死ねば OS が解放する。ロックが取れない親は、停止記録も通知も作らずに exit 4 で終わる。ack も同じロックを取るので、親の実行中には ack できない。

### 2.5 通知（メール経路）

- 停止：種類 `parent_stopped`、対象 `choice-parent-stop:<stop_id>`（停止ごとに別のイベントになる）。
- 全70完了（D6）：種類 `all_complete`、対象 `choice-parent-complete:<registration_id>`（再起動しても同じイベント1つ）。文面は「登録範囲の実行と正式記録が完了（分析は未実施）」。監視の `expected_completed_targets` は触っていない。
- どちらも `watch.save_event` で監視の `events/` に置く（`simulation_watch_event_v1`、イベントIDは対象と種類から決まるので冪等）。AIなしの方針により `ai_diagnostics=False`（`delivery: not_applicable`）。`mail_enabled: true` の監視または送信ワーカーが `sync_mail_outbox` でキューに入れる。メール本文に出るのは `status`（停止コード・段階・run・理由を1行にまとめたもの）と `source`（停止記録のパス）。

### 2.6 チェックポイント（D5）

設定ファイル（任意）：

```json
{"schema": "choice_parent_loop_settings_v1", "checkpoint_recorded_counts": [6]}
```

- 「記録済みが N件になった時点で一度止まる」。値はコードに書かず、既定は無し。値は 1〜(登録数−1) の重複しない整数に限る（それ以外は exit 64）。
- 停止コード `CHECKPOINT_REACHED`。ack 後に再起動すると、同じ N では再び止まらない（ack 済みのチェックポイント記録で判定）。親が記録直後に落ちても、次の起動で同じ判定が働く。
- 例の `[6]` は、学校PCの最初のセル（登録上の6番目）の後で止めて人が照合する場合の値。**実際の値はユーザーが決める。**

### 2.7 D3（`choice_core_sequence.py` の変更）

- **core計算中（`wait_core`）に限り**、監視だけの途切れ（`ObserverGap`）を待つ。上限は監視の設定 `07_監視システム/config.json` の `stale_sec`（現在600。新しい数は作らず、sequence 開始時に読み、state に `observer_gap_limit_sec` として残す）。
- 待つ間も `choice_monitor.py`（core を直接見る別経路）は毎回呼び、異常フラグが出れば即停止する。上限を超えたら `Independent observer gap exceeded…` で停止（既存と同じく保全）。
- `ObserverGap` になるもの：監視の鮮度切れ・生存していない・PIDと作成時刻の不一致（監視の再起動中）、state の監視本人と live の本人の不一致、対象の観測が120秒を超えて古い、**監視側が対象を読めていない（`read_failures` があり、manifest SHA が一致しない）**。
- 即停止のまま残したもの：監視のソースSHAがピン留めと違う、対象の異常フラグ・本人の不一致、未来の観測時刻、起動段階（start-next 前の監視確認・起動待ち）・finish・readback・sync の各段階、ピン留めSHAの変化、PIDの再利用など。`ObserverGap` は `RuntimeError` の子なので、core 以外の段階では従来どおり即停止になる。
- 監視が再起動して、同じソースSHA・鮮度120秒以内で戻ったときは新しい本人を受け入れ、`choice_sequence_observer_identity_changed` を operations.jsonl と monitoring.jsonl に残す。待機の開始・終了・超過と最大経過秒も同じく残し、sequence の state の `observer_gap` に書く。
- **「対象をまだ見つけていない」（対象エントリが無い、または読取失敗なしでSHAが合わない）は、既存の60秒の発見猶予のまま**にした。既存試験 `test_persistent_discovery_still_stops_after_its_own_60_seconds` を全件PASSのまま保つため（§5-1 を参照）。
- 共通5本・実行環境の指紋・READYへの影響：設定の `implementation_files`（共通5本）、`jdrt_choice_toolchain.py`、`jdrt_realtime_choice_validate.py`、`realtime_choice_cell.py`、現行 `preflight_ready.json` のいずれも `choice_core_sequence`・`watch.py`・`07_監視システム` を参照していないことを読取で再確認した。**影響なし。**
- 編集の前に、監視の state.json（active な対象0件、観測12秒前）、全系列の manifest（RUNNING 0件）、`writer.lock` なしをファイルとして読み、実行中の研究runが無いことを確認した。

## 5. 未実装・未確認・限界

1. **発見60秒は変えていない。** 実際の停止2件（2026-10-30、sq26103005・sq26103006）はどちらも `Independent target discovery remains unproven`（core段階）だった。sq26103005 の診断（`06_研究結果/jdrt/goal_20261017/sequence_discovery_failure_20261030/sq26103005/diagnosis.md`）では、原因は監視側の CIM 照会タイムアウトで、対象エントリは `read_failures: 2` だった。この型は今回の変更で `ObserverGap` になり、stale_sec まで待つ。一方 sq26103006 の保存エントリは `read_failures` が無く、`state_sha256` はあるが manifest と一致しない型で、**今回の変更でも60秒で止まる**。原因は未確認（manifest の更新が監視の観測より速い等の可能性。確かめていない）。D3 の「target をまだ見つけていない」状態まで待つには、既存試験の契約（60秒で停止）を変える判断が要る。
2. **監視の再起動が必要（SP-17）。** `watch.py` を変えたので、ディスク上のソースSHAは `78011056…` になった。稼働中の監視は以前から古いソース（`908cff…`）のまま。このままでは、親の事前確認（`MONITOR_NOT_PROVEN`）と core_sequence の `observer()` の両方で最初に止まる。学校PCでは最新ソースで監視を起動してから親を始める。
