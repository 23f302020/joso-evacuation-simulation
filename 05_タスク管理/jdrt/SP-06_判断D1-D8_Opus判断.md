## 2. D1：INVALID・FAILED セルの自動再実行 — **不採用**

| 項目 | 内容 |
|---|---|
| 結論 | 親は **reject・recover・再実行のどれも自動で行わない**。INVALID・FAILED・孤児を検出したら、状態を変えずに停止し、通知する |
| 根拠 | ① P88 は「保全・後続停止」を求め、新IDでの修復は「技術失敗の理由を記録」してから行うと定めている。理由の判定（技術失敗か、物理・会計の不合格か）は診断であり、機械的な分類規則は事前登録されていない。② 不合格を自動で取り直す運用は、合格するまで引き直す選択と区別できない（C37、P76）。③ R60 は reject・recover を、理由を記録する復旧操作と位置づけ、受入検査の失敗を無視する許可ではないとしている。④ sv26103006 の再実行も、ユーザーが個別に判断した（X23） |
| PAP・登録への影響 | なし。P88 をそのまま実装する |
| 親ループへの指示 | 1) §2.2 の #6・#11・#13・#14・#15 と、finish 内の validate 不合格を検出したら、`reject`・`recover`・`start-next` を呼ばずに停止する。2) 停止イベントには run_id、cell_id、段階（start／core／finish）、元のログのパスを入れる。結果の数値（受入数など）は入れない。3) 同じ prefix・同じセルで2本目を開始するコードを持たない（`choice_core_sequence.py` は `prefix+(N+1)` を使うので、同じセルを取り直すには新しい prefix が要る。親はこの経路を実装しない） |
| 人が再実行を決めた場合の扱い（参考） | 再実行は P88 に従い、理由を記録した reject の後、新しい run ID で行う。不合格のrunは削除せず、最終の結果一覧に「同じ版で除外したrunの履歴」として必ず併記する（v2 の結果一覧と同じ扱い。SKILL:80） |
| 残るリスク | 技術的な一時障害（OS再起動など）でも人が来るまで止まるので、無人運転の継続性は下がる |

## 3. D2：止まった後に完走したcoreの自動 finish — **不採用**

| 項目 | 内容 |
|---|---|
| 結論 | 親は `choice_core_sequence.py` の外で finish（check→validate→record）を呼ばない。系列が例外で止まったら、`unrecorded` が hold として残ったまま停止する |
| 根拠 | ① finish は正式採用を伴い、record は元に戻せない（PREPARED 状態でなければ recover-record で戻せない）。② 停止理由を例外の文字列から分類して自動で採用へ進めると、分類の誤りがそのまま記録の誤りになる。③ D3 で短い途切れは系列の中で吸収するので、残るのは長い途切れや異常である。これは人が見るべき場面であり、自動化の利点は小さい |
| PAP・登録への影響 | なし |
| 親ループへの指示 | 1) 例外で止まった系列の state（`FAILED_PRESERVED`、`child_may_still_be_running: true`）を読み、通知だけを出して終了する。2) 親が再起動したときも、同じ系列は再開しない。status に hold があれば停止を続ける（§5 の1行目） |
| 再開する人への注意（結果の選別を防ぐため） | 完了したcoreは、**結果を見てから捨てない**。SKILL:40 の再開手順どおり、まず既存の `choice_finish_cell.py` で独立validateにかける。PASS なら記録し、INVALID なら D1 の扱いにする。完了coreを validate にかけずに reject しない |
| 残るリスク | 夜間に長く途切れると、朝まで記録が進まない（研究結果には影響しない） |

## 4. D3：監視の一時的な途切れ — **条件付き採用（短い待機）**

| 項目 | 内容 |
|---|---|
| 結論 | **core計算中（`phase == 'core'`）に限り**、独立監視の「鮮度切れ・PIDの交代・target をまだ見つけていない」状態を、最大 **600秒** まで待つ。その間も `choice_monitor.py`（coreを直接見る別経路）は60秒ごとに呼び続け、`anomaly_flags == []` を必須にする。600秒を超えたら、今と同じく例外で停止する |
| 即停止のまま残すもの | ① 監視のソースSHAがピンと違う（一時的ではない）。② startup・finish・readback・sync の各段階（採用に直結するため厳しいまま）。③ `choice_monitor` の異常フラグ、PID の再利用、ピン留めSHAの変化など、監視の途切れ以外のすべて |
| 根拠 | ① 監視は研究の受入ゲートではない。採用は validate と record だけで決まる（P88、S30）。待っても研究状態は変わらない。core は系列が止まっても動き続ける（停止条件表 §5）。② 監視は毎分の救済で再起動するので、PID が変わることは想定内である（停止条件表 §5 の2行目）。③ 600秒は監視の既存の停滞判定値（`stale_sec=600`、停止条件表 §5）で、新しい数を作らないためにこれに合わせた |
| PAP・登録への影響 | なし。`choice_core_sequence.py` は共通5本にも runtime 指紋にも入っていないので、READY と既存記録の同一性に影響しない（§0 の確認） |

## 11. ユーザーが後から覆すべきか確認したい点

1. **D2 を不採用にしたこと。** 監視が10分を超えて途切れると、完了したcoreは朝まで記録されない。「監視系だけの停止なら自動 finish してよい」とする選択もありうる（研究上の選別にはならない。完了coreを必ず validate にかけるため）。無人運転の継続を優先したい場合は覆してよい。
2. **D3 の待機上限 600秒。** 監視の既存の停滞判定値に合わせただけで、根拠のある最適値ではない。
3. **D5 の解釈。** context.md:23 から「旧PCの5件は70件に数える」と読んだ（推測）。旧5件も学校PCで取り直す方針だった場合は、D5 の全体を見直す必要がある。ただし旧5件だけを取り直して良いほうを選ぶ運用は、どちらの場合も行わない。
4. **D5 の「最初の学校PCセルの後で一度止める」こと。** 出力に時刻やパスが入っていて、比較が常に不一致になる場合は、この停止を外すか、比較する出力を限定するかを決めてほしい。
5. **D6 で監視の全完了通知を出さないこと。** 親が強制終了されたときの完了の知らせがなくなる。冗長な通知が欲しい場合は、「要確認」の文面で監視側にも設定できる。
6. **D1 の「不合格runの履歴を最終一覧に併記する」こと。** これは開示を増やすだけで、除外規則の変更ではないと判断した。異なる理解であれば知らせてほしい。
