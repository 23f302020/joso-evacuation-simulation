更新日：2026-10-20。プロジェクト専用・外部由来・共通支援を区別せず、この研究で使うスキルとエージェントの選択、起動条件、モデル分担、委任境界、更新管理をここに集約する。

旧`外部スキル運用.md`を改名・拡張し、`モデル運用基準.md`の現行ルールと履歴を統合した。旧モデル文書は移転案内だけとし、独立した基準を維持しない。個別`SKILL.md`は実行手順、TOMLは実行設定、検証報告・JSON台帳は証跡であり、この運用正本の重複文書ではない。

## 0. モデル・研究判断・委任の共通ルール

- 最新のユーザー指定を優先する。定型監視・証跡抽出・記録は`gpt-6-luna / low`、異常解析・複雑な実装・研究判断案・数式考察は`gpt-6.1-sol / high`という現行指定を引き継ぐ。役割ファイルの値と起動要求、実backendの独立確認結果を区別する。
- 親chatの選択モデルと推論設定を維持する。文書やスキルの編集は実モデルの切替ではない。モデル名だけを理由に作業停止、別chat作成、必須引継ぎを行わない。
- 別エージェントはユーザーまたは適用指示の明示委任がある場合だけ起動する。上記の役割分担やスキル自動選択は委任許可を追加しない。許可された委任では所有対象、必要な証跡、許可操作、停止条件を指定し、他担当の変更を戻さない。
- 起動tool上必要なら`fork_turns=none`と明示model/effortで必要最小限の入力を渡す。起動要求値を記録し、確認できない実backendを推定しない。同時start/record/recoveryの所有者は一人とし、重複core・複数writerを作らない。
- 定型担当は異常を再解釈せず、後続を止めて一次証跡を判断担当へ戻す。現在の担当が許可範囲の調査・技術修正・検証・記録を進めてよく、通常作業の逐次承認や旧モデル固定分担は要求しない。
- 独立検証は一次成果物からの再計算で行う。別モデルの同意、persona、成功表示だけでは代替しない。モデルに合わせて入力・実装・受入条件を変えない。
- 方法変更は、事実確認→選択肢・根拠・不確実性の整理→ユーザー判断→事前登録→実装・検証の順とする。PAP、比較方式、主要指標、除外規則の未承認変更は行わない。モデル能力と研究方針の承認権限は別である。
- 判断記録には、判断日、担当と設定の確認範囲、ユーザー指示、前提正本、結論、根拠・代替案・不確実性、項目別確信度、状態、波及タスクを残す。入力数値を実ファイルで確認し、事実・推論・未確定を分ける。過去メモのモデル名や保存先は改名しない。
- 同種作業が2回以上発生したら既存スキルを再利用し、実証された不足だけ拡張する。異常時は原本・失敗run・SHA・ログを保全する。現在値は`context.md`、実験条件は対象PAP/Registry、実行・採用は専用スキルの正本へ戻る。
- モデル選択自体を依頼された場合は最新の公式資料と利用可能性を確認し、同じ代表課題の品質・時間・費用で判断する。旧文書にある過去のモデル推薦や分担を現在の指定へ上書き適用しない。

## 併用とエージェントの境界

- Pythonの不具合修正：デバッグで原因を絞り、TDDとPython試験で修正を確かめ、完了前に差分レビュー。同じ検証結果は再利用し、スキルごとに重複実行しない。
- 新規Pythonロジック：TDDとPython試験から開始し、完了前に差分レビュー。予期しない失敗が出たらデバッグを加える。
- 性能改善：性能解析を主とし、必要な変更検証と差分レビューを併用。SUMO/native/buildの時間をPython処理時間と区別する。
- JDRTのstatus/start-next/check/validate/record/recovery：引き続き`joso-jdrt-runner`が正本。異常時の技術診断に上記スキルを追加する。レビュー/TDDの合格からcore開始・record権限やREADYを推定しない。
- 既存の`research-status-publisher`は明示された公開依頼だけに適用する。今回の導入から外部送信・自動公開権限を推定しない。

5スキルは通常、作業中の親chatが使う。別エージェントは、ユーザーまたはその作業に適用される指示が明示的に委任を求めた場合だけ起動する。今回の「起動条件を定義する」依頼は将来の一律並列化の許可ではない。委任が許可された場合も、所有対象、入出力、許可操作、停止条件を指定し、同時record writerや重複coreを作らない。

モデル選択と委任は本書§0に従う。上流のモデル名をimportしない。

### モデル運用基準

> 作成日：2026/07/09  
> 現行運用更新：2026/10/18
> 目的：本研究で使用するAIモデル・エージェントの役割分担を固定し、判断の再現性と記録の一貫性を担保する。

> **適用上の注意：** 現在の運用は§0。§1〜§4はPhase 3当時の分担・判断記録を保全した履歴であり、現在のモデル名・利用可能性・必須引継ぎを規定しない。研究条件変更の判断権限はモデル能力と区別する。

#### 0. 現在の適用（現行系列全体）

- 2回以上発生した同種作業は既存スキルへ集約し、既存があれば再利用し、不足だけ拡張する。
- 定型監視・記録など思考負荷が低い作業は`gpt-6-luna low`を第一候補とし、必要品質を保つ範囲でモデルを下げるか試行量を抑える。
- 判断、異常解析、複雑な実装、数式による考察など判断負荷が高い作業は`gpt-6.1-sol high`を使用する。
- 定型記録の担当者は異常を独自に新解釈せず、事実と証跡を記録して判断担当へ戻す。
- モデルの能力と研究方針の承認権限は別であり、未承認の研究条件をモデル判断で変更しない。
- 最新のユーザー指定を優先し、定型はLuna low、判断負荷が高い作業は6.1 Sol highとする。本親chat自身の実設定は変更できない。
- 独立検証は一次成果物から再計算し、別モデルの追認だけで代用しない。

- ユーザーの明示指示により、現在のCodexは対象となる事前登録済み系列の技術実装、1セルずつのrun、独立検証、記録、登録済み分析を継続してよい。対象系列と現在地はcontext.mdで確認する。
- 実行順と記録は`.agents/skills/joso-jdrt-runner/`、現在値は`context.md`、方法と固定値は作業対象系列のPAP・Parameter Registryを正本とする。
- 単一セルの結果を理由にPAPやパラメータを変更しない。
- 新しい方法論判断が必要な場合は、現担当が実測に基づく論点・代替案・影響を整理し、ユーザーの明示判断を得て事前登録する。旧§3の特定モデルへの引継ぎは現在の必須条件ではない。
- モデル名や利用可能性が将来変わっても、役割の原則である「事実確認」「方針判断」「記録」「独立検証」の分離を維持する。

##### 能力に基づく運用

- 現担当は調査、設計、新規実装、修正、検証、記録、登録済み分析を一貫して進めてよい。通常作業でモデル交代や段階ごとの承認を要求しない。
- ユーザーの選択モデルと推論設定を維持する。この文書を編集しても実際のモデル設定は切り替わらない。
- モデル選択を依頼された場合、公式ガイドの現在の例ではLunaは範囲の明確な反復作業、GPT-6.1 Solは複雑な技術作業と時間・費用の両立、Astraは曖昧な問題や深い分析に位置付けられる。これは2026-10-09の参照例であり、全製品・アカウントでの利用可能性を保証しない。
- 推論量は同じ代表課題で比較し、必要品質を満たす設定を選ぶ。すべての作業をlow/mediumに固定したり、常に最高設定を求めたりしない。
- 異常時は後続runを止め、SHA・会計・ログ・一次成果物から診断する。現在の担当が扱える技術診断・復旧は進め、未解決の能力不足がある場合に具体的な理由とモデル変更案を提示する。
- 独立検証は生成側の判定だけに依存せず一次成果物から再計算する。別モデルの同意を独立検証の代わりにしない。

##### 現在の研究判断と記録

事実確認→選択肢・根拠・不確実性の整理→ユーザーの方針判断→事前登録→実装・検証の順とする。現担当は調査と判断案作成を行えるが、未承認のPAP・比較方式・除外規則を変更しない。既存手順に沿う技術作業は継続する。

判断日、担当（分かる範囲のモデル・推論設定）、ユーザー判断の出典、前提正本、結論、項目別確信度、状態、波及タスクを記録する。数値は実ファイルで検証し、事実・推論・未確定事項を区別する。過去メモのモデル名と保存先は改名しない。

根拠（2026-10-09確認）：[公式モデル選択](https://developers.openai.com/api/docs/guides/model-selection)、[強いモデル向け指示の見直し](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)。具体的な研究承認境界はこのプロジェクトの規則である。

#### 3. 研究方針の判断プロセス（3段階分離）

方針判断は必ず次の順で行い、各段階を別モデルが担当する。

```
論点整理（Opus）→ 判断（Fable 5）→ 記録（Sonnet 5 または Opus）
```

| 段階 | 担当 | やること | やらないこと |
|------|------|---------|-------------|
| **論点整理** | Opus | 関連文書・実装・実測値を読み、事実と論点を抽出して判断者に渡す | 結論を出さない |
| **判断** | Fable 5 | 方法論上の決定を下す。提案の追認ではなく批判的検証を行う | ファイルの作成・編集をしない |
| **記録** | Sonnet 5 / Opus | 判断内容を既存書式のメモに書き起こす | 数値を再導出しない・判断を変えない |

##### 段階分離の理由

- 論点を整理したモデルがそのまま判断すると、自らの整理の枠内でしか結論が出ない。判断者を分けることで前提そのものを疑える。
- 記録者は判断結果を写すだけに徹する。数値の再導出を許すと、記録段階で判断と食い違う値が混入する。
- **判断の入力となる数値は、記録前に必ず実ファイルで検証する**（判断が誤った数値の上に立っていないことを担保するため）。

##### 判断メモの保存先

`開発メモ/方針判断_fable5/{段階フォルダ}/{論点名}_方針判断_fable5.md`

書式は `車両会計_方針判断_fable5.md` に揃える（メタ情報テーブル → 判断 → 根拠 → 確定パラメータ表 → 留意点・未解決 → 波及タスク → 確信度 → 参照）。メタ情報テーブルには必ず「プロセス」欄を設け、担当モデルを明記する。

> **注意：** `開発メモ/` は `.gitignore` 対象のため、判断メモはリモートに残らない（ローカル運用）。

---

#### 4. 判断メモに必須の記載事項

| 項目 | 内容 |
|------|------|
| 判断日 | 絶対日付で記す |
| プロセス | 論点整理・判断・記録の担当モデル |
| 前提正本 | 判断が依拠する確定済み文書のパス |
| 結論 | 1〜2文で判断の核心 |
| 確信度 | 項目別に 高／中／低 を付す（総合だけでは不可） |
| 状態 | 方針確定か、実装着手済みか |

確信度を項目別に付すのは、後続タスクが「どの前提から検証すべきか」を判断できるようにするため。
