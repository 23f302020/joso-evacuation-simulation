# スキル・エージェント運用 — 本プロジェクトの正本

更新日：2026-10-21。プロジェクト専用・外部由来・共通支援を区別せず、この研究で使うスキルとエージェントの選択、起動条件、モデル分担、委任境界、更新管理をここに集約する。

旧`外部スキル運用.md`を改名・拡張し、`モデル運用基準.md`の現行ルールと履歴を統合した。旧モデル文書は移転案内だけとし、独立した基準を維持しない。個別`SKILL.md`は実行手順、TOMLは実行設定、検証報告・JSON台帳は証跡であり、この運用正本の重複文書ではない。

## 0. モデル・研究判断・委任の共通ルール

- 最新のユーザー指定を優先する。定型処理は`gpt-6-luna / low`、仕様と受入条件が明確な通常開発は`gpt-6.1-sol / medium`、難しい診断・検証設計・研究判断案は`gpt-6.1-sol / high`を第一候補とする。限定された未解決の難問だけ`gpt-6-astra / high`を比較候補とする。詳細は§0.1。役割ファイルの値と起動要求、実backendの独立確認結果を区別する。
- 親chatの選択モデルと推論設定を維持する。文書やスキルの編集は実モデルの切替ではない。モデル名だけを理由に作業停止、別chat作成、必須引継ぎを行わない。
- 別エージェントはユーザーまたは適用指示の明示委任がある場合だけ起動する。上記の役割分担やスキル自動選択は委任許可を追加しない。許可された委任では所有対象、必要な証跡、許可操作、停止条件を指定し、他担当の変更を戻さない。
- 起動tool上必要なら`fork_turns=none`と明示model/effortで必要最小限の入力を渡す。起動要求値を記録し、確認できない実backendを推定しない。同時start/record/recoveryの所有者は一人とし、重複core・複数writerを作らない。
- 定型担当は異常を再解釈せず、後続を止めて一次証跡を判断担当へ戻す。現在の担当が許可範囲の調査・技術修正・検証・記録を進めてよく、通常作業の逐次承認や旧モデル固定分担は要求しない。
- 独立検証は一次成果物からの再計算で行う。別モデルの同意、persona、成功表示だけでは代替しない。モデルに合わせて入力・実装・受入条件を変えない。
- 方法変更は、事実確認→選択肢・根拠・不確実性の整理→ユーザー判断→事前登録→実装・検証の順とする。PAP、比較方式、主要指標、除外規則の未承認変更は行わない。モデル能力と研究方針の承認権限は別である。
- 判断記録には、判断日、担当と設定の確認範囲、ユーザー指示、前提正本、結論、根拠・代替案・不確実性、項目別確信度、状態、波及タスクを残す。入力数値を実ファイルで確認し、事実・推論・未確定を分ける。過去メモのモデル名や保存先は改名しない。
- 同種作業が2回以上発生したら既存スキルを再利用し、実証された不足だけ拡張する。異常時は原本・失敗run・SHA・ログを保全する。現在値は`context.md`、実験条件は対象PAP/Registry、実行・採用は専用スキルの正本へ戻る。
- モデル選択自体を依頼された場合は最新の公式資料と利用可能性を確認し、同じ代表課題の品質・時間・費用で判断する。旧文書にある過去のモデル推薦や分担を現在の指定へ上書き適用しない。

### 0.1 作業別モデル選択

以下は2026-10-21のユーザー承認方針であり、公式の品質保証や自動モデル切替ではない。通常開発の第一候補をSol mediumとし、Lunaへの開発委任拡大は代表課題で品質と手戻りを確認してから判断する。

| 作業 | 第一候補 | 担当範囲・切替条件 |
|---|---|---|
| PID・ログ更新・状態変化の平常監視 | LLMなし | 既存の独立監視を利用。変化がなければAI確認を追加しない |
| 既知イベントの短報・証跡一覧・転記 | Luna low | 固定項目の抽出。欠損・不一致・未知状態を解釈で補わない |
| 誤字・リンク・既存書式修正、経過報告の整形 | Luna low | 確定事実の編集。研究上の意味・結論・限界の判断はSol high |
| 正常な実験操作・validate・同期record | Luna low | 対象系列の開始条件・担当権限を満たし既存helperで処理できる場合だけ。異常時は後続を止める |
| 局所的な実装・CLI・監視・記録helper開発 | Sol medium | 仕様と受入条件が明確で局所回帰試験が可能。部分書込・排他・復旧など複数状態の難しい判断はhigh |
| Python試験の追加・修正 | Sol medium | 既知の境界・再現済み不具合。期待値や契約の設計が必要ならhigh |
| SUMO・TraCI・nativeの異常解析 | Sol high | 位置・時計・経路・stageなど複数層にまたがる原因調査 |
| validator・人物会計・SHAゲート変更 | Sol high | 見落とし・誤検出・受入契約と独立検証の設計 |
| CSV等の性能改善 | Sol medium → high | 実測・局所I/O改善はmedium。意味同一性・並列処理の判断が難しければhigh |
| 資料の数値・出典抽出 | Luna low | 出典箇所・対象年・地域・母数の抽出。資料間の矛盾・採否判断はSol high |
| 資料比較・GIS入力監査 | Sol high | 出典の独立性、CRS、時空間対応、採用根拠と不足を照合 |
| 登録済み集計・図表の実装 | Sol medium | 固定済みの式・分母・出力仕様に従う。結果監査・主張の成立条件はhigh |
| 結果監査・数式考察・研究判断案 | Sol high | 一次成果物から分母・結合・打切り・時計と主張を照合。方法変更の承認権限は増えない |
| Sol highでも残る限定された難問 | Astra highを比較候補 | 再現条件・仮説・反証・未解決論点を整理して投入。常用役や専用agentは追加しない |

略記：Luna=`gpt-6-luna`、Sol=`gpt-6.1-sol`、Astra=`gpt-6-astra`。xhigh以上は個別課題で効果を確認した場合だけ候補にし、一律には指定しない。

振分けは、手順と確認方法が固定済みならLuna、正解が明確で実装が必要ならSol medium、原因・正解・検証範囲の設計が必要ならSol highとする。同じvalidator作業でも既存検証器の実行と見落とし修正を分ける。同じ失敗への根拠のない再試行を続けず、再現条件・試した仮説・一次証跡をまとめて判断負荷を再評価する。担当の能力限界が具体化した場合に切替を提案し、現在の親chatで可能な調査・検証は継続する。

根拠：[公式モデル選択](https://developers.openai.com/api/docs/guides/model-selection)、[公式推論量説明](https://developers.openai.com/api/docs/guides/reasoning)。参照確認は2026-10-21の提案時。API料金・トークン数・Codex利用枠消費は別であり、節約率は未測定。

### 0.2 読込・出力・引継ぎと品質の維持

- 通常は本書の§0〜研究用エージェントまでと、該当作業のスキル節だけを読む。「履歴：統合前」以降は過去判断が必要な場合だけ読む。同じchatで有効な指示を繰り返し全文取得しない。
- 全ログはファイルへ保全し、chat出力は状態・前回からの変化・失敗箇所・証跡パスを中心にする。要約で不一致や未検証範囲を落とさない。待機中は既存handle/監視を再利用し、重複run・重複監視を作らない。
- 許可された委任は独立した作業に限定する。全履歴forkを既定にせず、必要なら`fork_turns=none`で下記の短い引継ぎを渡す。新agentにも該当する正本と指示の読込を求め、別担当の変更を戻させない。振分け専用LLMや分野別の多数のagentは追加しない。
- 検証証跡を再利用できるのは、対象コード・入力・検証器・関連依存のSHA/版と必要な検証範囲が一致し、有効性を確認できる場合だけ。変更の影響範囲・欠損・不一致があれば必要な検証を実施する。専用recordが再検証を要求する場合は省略しない。
- モデルを軽くしても、全件会計・SHA・manifest・独立再計算・必要な回帰試験・開始/採用ゲートは削らない。別モデルの追認は独立検証ではない。

引継ぎは既存のタスク記録・証跡を参照し、運用正本を増やさない。

```text
目的と受入条件：
担当ファイル・許可操作・他担当との境界：
対象系列・固定契約・読むべき正本/スキル：
現在の証跡パス・SHA/版・検証範囲・最終観測時刻：
次の操作・既存run ID/handle・停止条件：
未解決事項・既に試した仮説と結果：
要求モデル/推論量・実backendの確認範囲：
```

### 0.4 判断と結果を次の実行へ生かす統一運用（2026-10-22整理）

ユーザー「どの判断をしたらどんなことが起きたか（ミス・成功含めて）を記録していき」を受けた仕組みは、ACEを含む以下の一つの流れで運用する。ACE導入前の手作業による教訓一覧の独立更新は終了する。

**ACEの判断基準を確認 → 判断を記録 → 実行して結果を追記 → 必要な教訓だけACEへ反映**

| 役割 | 保存先・入口 | 更新する内容 |
|---|---|---|
| 運用手順の正本 | 本節 | いつ・誰が・何を記録/参照するか |
| 判断と結果の根拠 | [判断と結果の台帳](../00_全体整理/判断と結果の台帳.md) | 判断時の情報・選択・期待と、結果・失敗/成功・手戻り・一次証跡 |
| 現在使う判断基準 | `.agents/tools/ace/ace.ps1 show` | 台帳を根拠に整理した暫定教訓。本文はACEの最新snapshotを正本とし、別の手編集一覧を維持しない |
| コマンド・導入/保守の説明 | [ACE README](../.agents/tools/ace/README.md) | delta書式・配置・監査・再構築。運用ルールを別に定義しない |

1. **判断前**：各作業chatは重要な判断の前にACEの`show`から関連基準と根拠事例を確認する。確認した基準IDと、今回への適用理由または適用しない理由を短く残す。同じ作業内で有効な表示を保持している場合は基準ID/表示時点を参照して再実行を重複しない。適用条件の違いを確かめ、台帳の同じ判断IDに目的、確認済み事実/不明点、選択肢、理由、期待結果、成功/中止条件、証跡を記録する。既存の決定記録や検証報告はリンクで兼ねる。定型status・変化のない待機ごとには追加しない。
2. **結果後**：同じIDへ観測結果、期待との差、検出時点、手戻り、測定できた時間/消費/介入回数、未確認事項を追記する。後追い事例は明記し、当時の予測を創作しない。欠測を0にしない。研究セルの正式記録は既存の専用recordを使う。
3. **教訓への整理**：過去事例の比較と判断基準の整理は本chatが担当する。成功・失敗・未確定を併せて見て、適用条件→先に行う確認→中止/見直し条件を整理する。実行中の研究chatはACEの参照と、判断/結果/役立った・逆効果・未確定の台帳記録を担当する。ACEへのdelta適用は本chatだけが担当し、並行writerを作らない。
4. **ACEへの反映**：新しい教訓または既存基準の有用/有害評価が得られた時だけ、根拠事例ID付きdeltaを適用する。現在のchatが振り返りと整理を行い、実上流の更新処理が版・履歴を保持する。事例ごとの教訓は根拠記録として残し、台帳内の横断まとめ・調査表は履歴として保持する。現在の基準を台帳とACEの両方へ手入力しない。

結果の成否と、当時の情報に対する判断の妥当性は分けて評価する。早期の不具合検出・不正採用の防止も記録する。単発事例や単なる前後関係から因果・成功確率を断定しない。helpful/harmfulは根拠付きの評価数であり成功確率ではない。効果測定は比較可能な対象/期間の初回合格、回避可能な再実行、手戻り/総時間、重大な見落とし、消費、記録負担で行い、検証省略による短縮を改善としない。導入効果は未測定。

現在は固定上流82709de・別venvのローカル構成。根拠/元版/重複/単一writerを検査し、通信・子プロセスを拒否する。FiNER脆弱性のある評価経路は非使用、外部API自動LLMは未接続、別agentは自動起動しない。監査範囲・制約・20試験/初期5基準の導入証跡はREADMEから参照する。

PAP・主要指標・比較方式・除外規則・開始/採用ゲートの権限は既存規則に従う。実証された手順の不足は既存スキルへ最小反映し、旧版・理由・検証を残す。台帳/ACEは研究上の承認権限や自動復旧権限を追加しない。残る評価は、今後の判断事例を使った手戻り・総時間・記録負担の測定である。

## 併用とエージェントの境界

- Pythonの不具合修正：デバッグで原因を絞り、TDDとPython試験で修正を確かめ、完了前に差分レビュー。同じ検証結果は再利用し、スキルごとに重複実行しない。

- 既存の`research-status-publisher`は明示された公開依頼だけに適用する。今回の導入から外部送信・自動公開権限を推定しない。

#### 0. 現在の適用（現行系列全体）

- 2回以上発生した同種作業は既存スキルへ集約し、既存があれば再利用し、不足だけ拡張する。
- 定型監視・記録など思考負荷が低い作業は`gpt-6-luna low`を第一候補とし、必要品質を保つ範囲でモデルを下げるか試行量を抑える。
- 判断、異常解析、複雑な実装、数式による考察など判断負荷が高い作業は`gpt-6.1-sol high`を使用する。
- 定型記録の担当者は異常を独自に新解釈せず、事実と証跡を記録して判断担当へ戻す。
- モデルの能力と研究方針の承認権限は別であり、未承認の研究条件をモデル判断で変更しない。
- 最新のユーザー指定を優先し、定型はLuna low、判断負荷が高い作業は6.1 Sol highとする。本親chat自身の実設定は変更できない。
- 独立検証は一次成果物から再計算し、別モデルの追認だけで代用しない。

- ユーザーの明示指示により、現在のCodexは対象となる事前登録済み系列の技術実装、1セルずつのrun、独立検証、記録、登録済み分析を継続してよい。対象系列と現在地はcontext.mdで確認する。
- 実行順と記録は`.agents/skills/joso-jdrt-runner/`、現在値は`context.md`、方法と固定値は作業対象系列のPAP・Parameter Registryを正本とする。
- 単一セルの結果を理由にPAPやパラメータを変更しない。
- 新しい方法論判断が必要な場合は、現担当が実測に基づく論点・代替案・影響を整理し、ユーザーの明示判断を得て事前登録する。旧§3の特定モデルへの引継ぎは現在の必須条件ではない。
- モデル名や利用可能性が将来変わっても、役割の原則である「事実確認」「方針判断」「記録」「独立検証」の分離を維持する。

##### 能力に基づく運用

- 現担当は調査、設計、新規実装、修正、検証、記録、登録済み分析を一貫して進めてよい。通常作業でモデル交代や段階ごとの承認を要求しない。
- ユーザーの選択モデルと推論設定を維持する。この文書を編集しても実際のモデル設定は切り替わらない。
- モデル選択を依頼された場合、公式ガイドの現在の例ではLunaは範囲の明確な反復作業、GPT-6.1 Solは複雑な技術作業と時間・費用の両立、Astraは曖昧な問題や深い分析に位置付けられる。これは2026-10-09の参照例であり、全製品・アカウントでの利用可能性を保証しない。
- 推論量は同じ代表課題で比較し、必要品質を満たす設定を選ぶ。すべての作業をlow/mediumに固定したり、常に最高設定を求めたりしない。
- 異常時は後続runを止め、SHA・会計・ログ・一次成果物から診断する。現在の担当が扱える技術診断・復旧は進め、未解決の能力不足がある場合に具体的な理由とモデル変更案を提示する。
- 独立検証は生成側の判定だけに依存せず一次成果物から再計算する。別モデルの同意を独立検証の代わりにしない。

##### 現在の研究判断と記録

事実確認→選択肢・根拠・不確実性の整理→ユーザーの方針判断→事前登録→実装・検証の順とする。現担当は調査と判断案作成を行えるが、未承認のPAP・比較方式・除外規則を変更しない。既存手順に沿う技術作業は継続する。

判断日、担当（分かる範囲のモデル・推論設定）、ユーザー判断の出典、前提正本、結論、項目別確信度、状態、波及タスクを記録する。数値は実ファイルで検証し、事実・推論・未確定事項を区別する。過去メモのモデル名と保存先は改名しない。

根拠（2026-10-09確認）：[公式モデル選択](https://developers.openai.com/api/docs/guides/model-selection)、[強いモデル向け指示の見直し](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)。具体的な研究承認境界はこのプロジェクトの規則である。

#### 3. 研究方針の判断プロセス（3段階分離）

方針判断は必ず次の順で行い、各段階を別モデルが担当する。

```
論点整理（Opus）→ 判断（Fable 5）→ 記録（Sonnet 5 または Opus）
```

| 段階 | 担当 | やること | やらないこと |
|------|------|---------|-------------|
| **論点整理** | Opus | 関連文書・実装・実測値を読み、事実と論点を抽出して判断者に渡す | 結論を出さない |
| **判断** | Fable 5 | 方法論上の決定を下す。提案の追認ではなく批判的検証を行う | ファイルの作成・編集をしない |
| **記録** | Sonnet 5 / Opus | 判断内容を既存書式のメモに書き起こす | 数値を再導出しない・判断を変えない |

##### 段階分離の理由

- 論点を整理したモデルがそのまま判断すると、自らの整理の枠内でしか結論が出ない。判断者を分けることで前提そのものを疑える。
- 記録者は判断結果を写すだけに徹する。数値の再導出を許すと、記録段階で判断と食い違う値が混入する。
- **判断の入力となる数値は、記録前に必ず実ファイルで検証する**（判断が誤った数値の上に立っていないことを担保するため）。

##### 判断メモの保存先

`開発メモ/方針判断_fable5/{段階フォルダ}/{論点名}_方針判断_fable5.md`

書式は `車両会計_方針判断_fable5.md` に揃える（メタ情報テーブル → 判断 → 根拠 → 確定パラメータ表 → 留意点・未解決 → 波及タスク → 確信度 → 参照）。メタ情報テーブルには必ず「プロセス」欄を設け、担当モデルを明記する。

> **注意：** `開発メモ/` は `.gitignore` 対象のため、判断メモはリモートに残らない（ローカル運用）。

---

#### 4. 判断メモに必須の記載事項

| 項目 | 内容 |
|------|------|
| 判断日 | 絶対日付で記す |
| プロセス | 論点整理・判断・記録の担当モデル |
| 前提正本 | 判断が依拠する確定済み文書のパス |
| 結論 | 1〜2文で判断の核心 |
| 確信度 | 項目別に 高／中／低 を付す（総合だけでは不可） |
| 状態 | 方針確定か、実装着手済みか |

確信度を項目別に付すのは、後続タスクが「どの前提から検証すべきか」を判断できるようにするため。
