# Phase 2 実装前仕様

> 作成日：2026/05/14  
> 目的：Phase 2 実装に入る前に、判断事項の採用案と理由を固定する。  
> 対象：常総市実データ版、シナリオA（自家用車のみ）

---

## 1. 仕様固定の基本方針

Phase 2 は、Phase 1 の道路閉鎖・避難ルート探索を SUMO/TraCI に接続し、自家用車避難の交通流ベースラインを作る。

採用方針は、以下を優先して決めた。

1. 卒論本文で説明しやすいこと
2. 先生コメントに直接対応できること
3. 実装リスクを小さく段階的に進められること
4. Phase 3 のバス・デマンド交通比較に接続できること

---

## 2. 採用した判断一覧

| ID | 項目 | 採用案 | 理由 |
|---|---|---|---|
| JUDGE-1 | SUMO導入 | 公式インストーラで導入 | Windows環境で安定し、卒論の実装環境として説明しやすい |
| JUDGE-2 | `traci` / `sumolib` | SUMO付属ライブラリを `SUMO_HOME` 経由で参照 | SUMO本体とPythonライブラリのバージョン不一致を避けるため |
| JUDGE-3 | 避難所安全性 | 浸水リスクあり避難所は原則目的地から除外 | 「安全な避難所への避難」として先生コメントへ対応できるため |
| JUDGE-4 | 1/10試行 | 小規模テスト → 全メッシュ保持・車両数1/10 → 全量 | 空間分布を保ちながら、段階的に負荷を上げられるため |
| JUDGE-5 | 車両台数換算 | 小規模は1メッシュ1台、1/10以降は世帯換算 | 実装確認と研究妥当性を両立できるため |
| JUDGE-6 | 出発時刻 | 基本は一斉出発、後で30分分散を感度分析 | 最悪ケースとして渋滞が出やすく、比較基準を作りやすいため |
| JUDGE-7 | 時間軸 | t0〜t7を6時間へ線形圧縮 | 実行負荷を抑えつつ、時系列閉鎖の変化を全て使えるため |
| JUDGE-8 | 閉鎖道路上の車両 | 再経路探索し、失敗または長時間停止で逃げ遅れ候補 | 即時逃げ遅れ扱いより現実的で、過大評価を避けられるため |
| JUDGE-9 | 逃げ遅れ定義 | 複数条件を出し、主指標は「未到着かつ到達不能または長時間停止」 | Phase 1との比較と渋滞影響の両方を説明できるため |
| JUDGE-10 | 保存形式 | 初回はCSV、重くなったらSQLiteへ移行 | 小規模・1/10試行で確認しやすく、必要時に拡張できるため |

## 3. 環境仕様

| 項目 | 採用仕様 |
|---|---|
| SUMO本体 | 公式インストーラで導入 |
| コマンド | `sumo`, `sumo-gui`, `netconvert`, `netedit` をPATHから実行可能にする |
| 環境変数 | `SUMO_HOME` を設定する |
| Python連携 | `SUMO_HOME/tools` を参照し、`traci` / `sumolib` を使う |
| pip導入 | 原則不要。SUMO付属ライブラリ参照で動かない場合のみ検討 |

## 4. 避難所安全性仕様

Phase 2では、目的地となる避難所の安全性を確認する。

| 項目 | 採用仕様 |
|---|---|
| 判定対象 | `04_プログラム/output/agents/shelters.csv` |
| 浸水リスクデータ | A31a最大浸水範囲、`waterDepth >= 2` |
| 判定方法 | 避難所点が浸水深0.5m以上ポリゴンに含まれるかを判定 |
| 目的地扱い | 浸水リスクあり避難所は原則として目的地から除外 |
| 例外 | 安全避難所が不足する場合は、リスク属性付きで別途記録し、主結果には含めない |
| 出力候補 | `shelters_safety.csv` |

理由：避難所自体が浸水する可能性があるという先生コメントに対応し、「避難所に着いたが危険」という評価の矛盾を避けるため。

## 5. 車両エージェント仕様

### 5-1. 実行段階

| 段階 | 内容 | 目的 |
|---|---|---|
| 小規模テスト | 1メッシュ1台、数台〜40台程度 | SUMOネットワーク・ルート・閉鎖処理の疎通確認 |
| 1/10試行 | 全メッシュを残し、車両数を1/10換算 | 空間分布を保った軽量シミュレーション |
| 全量実行 | 世帯換算に基づく車両数 | 最終的なシナリオA評価 |

### 5-2. 車両台数換算

| 項目 | 採用仕様 |
|---|---|
| 小規模テスト | 1メッシュ1台 |
| 1/10試行以降 | `total_pop / 2.3` を世帯数近似として車両台数化 |
| 1/10換算 | 全メッシュを残し、各メッシュの車両数を0.1倍 |
| 最小台数 | 人口があるメッシュは、1/10試行でも必要に応じて最低1台を許容 |

理由：Phase 2では自家用車避難の交通負荷を見るため、人口そのものより「世帯から発生する車両」に近い換算の方が説明しやすい。小規模テストだけは実装確認を優先する。

## 6. 出発時刻仕様

| 項目 | 採用仕様 |
|---|---|
| 基本ケース | 全車両がシミュレーション開始時刻に一斉出発 |
| 感度分析候補 | 30分の分散出発 |
| Phase 2最初の実装 | 一斉出発のみ |

理由：一斉出発は最悪ケースとして渋滞を確認しやすく、Phase 1の静的結果との差も説明しやすい。分散出発は追加比較として後から導入できる。

## 7. 時間軸仕様

Phase 2では、t0〜t7をSUMO上の6時間に線形圧縮する。

| 時点 | 実時刻 | 6時間圧縮SUMO秒 |
|---|---|---:|
| t0 | 2015-09-10 18:00 | 789 |
| t1 | 2015-09-11 06:00 | 2,620 |
| t2 | 2015-09-11 18:00 | 4,452 |
| t3 | 2015-09-12 06:00 | 6,284 |
| t4 | 2015-09-12 18:00 | 8,116 |
| t5 | 2015-09-13 06:00 | 9,948 |
| t6 | 2015-09-13 18:00 | 11,780 |
| t7 | 2015-09-16 10:20 | 21,600 |

理由：実時間のままでは最大509,400秒となり、試行負荷が大きい。6時間圧縮なら既存のモデル仮定に合わせつつ、t0〜t7の閉鎖変化を全て使える。

論文では「実災害の時間経過を完全再現したものではなく、道路閉鎖の進行を6時間シミュレーションに圧縮した検証用時間軸」と明記する。

## 8. 道路閉鎖・再経路探索仕様

| 項目 | 採用仕様 |
|---|---|
| 閉鎖対象 | `road_closure_timeline.json` をSUMO edge IDへ変換したもの |
| 閉鎖方法 | TraCIで対象edgeを通行不可にする |
| 閉鎖後の車両 | 再経路探索を試みる |
| 再経路不可 | 到達不能候補として記録 |
| 長時間停止 | 600秒以上停止した場合、逃げ遅れ候補として記録 |

理由：道路閉鎖直後に即時逃げ遅れ扱いにすると過大評価になりやすい。再経路探索を許可することで、Phase 1の迂回ルート探索との連続性も保てる。

---

## 9. 逃げ遅れ定義

Phase 2では、複数の状態を記録し、主指標を1つに固定する。

| 指標 | 定義 | 扱い |
|---|---|---|
| 未到着 | シミュレーション終了時に目的地へ到着していない | 補助指標 |
| 到達不能 | 再経路探索に失敗した | 逃げ遅れ候補 |
| 長時間停止 | 600秒以上停止した | 逃げ遅れ候補 |
| 浸水域内残存 | 閉鎖・浸水進行時点で浸水域内に残っている | 補助指標 |
| 主指標 | 未到着かつ、到達不能または長時間停止 | Phase 2の逃げ遅れ台数 |

理由：未到着だけでは時間切れと孤立を区別できない。到達不能・長時間停止を組み合わせることで、道路閉鎖と渋滞の影響を表しやすい。

## 10. 出力保存仕様

| 項目 | 採用仕様 |
|---|---|
| 初期出力 | CSV |
| 対象 | 小規模テスト、1/10試行、初回全量実行 |
| SQLite移行 | ログ量が大きく、CSV処理が重くなった場合に検討 |
| 主なCSV | `evacuation_summary.csv`, `vehicle_log.csv`, `closure_log.csv`, `congestion_log.csv`, `phase1_phase2_comparison.csv` |

理由：CSVは内容確認と卒論用表への転記が容易である。最初からSQLiteを導入すると実装量が増えるため、必要になった段階で移行する。

## 11. 成果物トップページ仕様

今後 `04_プログラム/output/index.html` を更新するときは、トップ画面を Phase 1 / Phase 2 / Phase 3 に分ける。

| 区分 | 表示する成果物 |
|---|---|
| Phase 1 | 道路閉鎖・避難ルート探索・茨城県統合シミュレーション |
| Phase 2 | SUMO自家用車避難シミュレーション、逃げ遅れ・渋滞指標 |
| Phase 3 | バス・デマンド交通追加、A/B比較、感度分析 |

理由：Phaseごとの成果物の性格が異なるため、トップ画面で分けることで、確認者がPhase 1の可視化成果とPhase 2以降の交通流結果を混同しにくくなる。
