## 1. システム概要

### 1-1. 目的

2015年9月 鬼怒川氾濫（茨城県常総市）を事例として、以下の2シナリオを交通流シミュレーションで比較する。

| シナリオ | 内容 |
|---------|------|
| **A（ベースライン）** | 全住民が自家用車で避難。車非保有者は迎え走行依存 or 孤立。 |
| **B（提案）** | 車非保有・高齢者がデマンド交通バス（5台）で避難。迎え走行が不要になり道路上の車両が削減。 |

### 1-2. 評価指標

| 指標 | 定義 | Phase |
|------|------|-------|
| 逃げ遅れ人数 | 浸水到達時に浸水エリア内に残るエージェント数 | 1〜3 |
| 避難完了時間 | 全対象エージェントが避難所に到達するまでの時間 | 1〜3 |
| 渋滞発生規模 | 主要避難路の平均速度・渋滞継続時間 | 2〜3 |
| バス輸送人数 | バスが輸送した延べ人数（シナリオB） | 3 |

### 1-3. シミュレーション時間設定

| 項目 | 値 |
|------|-----|
| 破堤時刻 | 2015/09/10 12:50（常総市三坂町） |
| シミュレーション開始 | 12:50（t=0） |
| シミュレーション終了 | 18:50（t=21,600秒） |
| 浸水状況更新間隔 | 30分ごと（1,800秒ごと） |
| KML時点数 | 8時点（最初の3時点が発災後6時間内の主要変化） |

## 4. データ入力仕様

### 4-1. 浸水KML（D1-No.917）

| 項目 | 値 |
|------|-----|
| ファイル形式 | KML（各時点1ファイル） |
| ジオメトリ型 | LineString のみ（Polygonなし） |
| 浸水深属性 | **なし**（深度情報は持たない） |
| 使用目的 | 各時点の浸水エリア境界 → 時刻別の封鎖タイミング決定 |
| 読み込み方法 | `geopandas.read_file(path, driver='KML')` |
| CRS | WGS84（EPSG:4326）→ 演算前にEPSG:6668へ変換 |

**処理方針：** KMLのLineStringはバッファ処理でPolygonに変換し、A31a GMLの waterDepth>=2 ポリゴンとの重ね合わせで封鎖エッジを確定する。

### 4-2. 浸水想定区域GML（A31a-2024）

| 項目 | 値 |
|------|-----|
| ファイル形式 | GML（国土数値情報） |
| フィーチャ型 | `ksj:PlanScale` |
| ジオメトリ型 | Polygon |
| 浸水深属性 | `ksj:waterDepth`（コード値 1〜6） |
| 対象河川 | 河川コードによる絞り込みなし（N03常総市境界クリップで地理的に限定） |
| 閉鎖対象 | `ksj:waterDepth >= 2`（0.5m以上） |
| CRS | JGD2011（EPSG:6668） |
| 読み込み方法 | `xml.etree.ElementTree`（pyogrioでA31a形式のxlink参照を解決できないため手動パース） |

**waterDepthコード値：**

| コード | 深さ |
|--------|------|
| 1 | 0〜0.5m未満 |
| **2** | **0.5〜3.0m未満 ← 閉鎖しきい値** |
| 3 | 3.0〜5.0m未満 |
| 4 | 5.0〜10.0m未満 |
| 5 | 10.0〜20.0m未満 |
| 6 | 20.0m以上 |

### 4-3. 250mメッシュ人口（T001178）

| 項目 | 値 |
|------|-----|
| ファイル | `tblT001178Q08.txt` |
| エンコーディング | Shift-JIS |
| KEY_CODE | 10桁（2次メッシュ6桁 + 250mメッシュ4桁） |
| 常総市メッシュ | KEY_CODE 先頭6桁 = `543907` または `543917` |
| 総列数 | 63列（col[0]=KEY_CODE, col[1]=名称, col[2]〜=人口データ） |

**注意：** 先頭1〜2行がヘッダのため `skiprows` の行数を実ファイルで確認すること。

### 5-2. e1_load_flood_data.py

**目的：** A31a GMLから浸水深>=0.5mのポリゴンを抽出し、KML時系列と組み合わせて時刻別浸水マップを構築する。

**統合戦略（Option B）：**
- A31a waterDepth>=2 → 「最終的に閉鎖されうる道路」の候補集合を確定
- KML時系列 → 各時点でどこまで浸水が進んでいるかの境界を取得
- 交差判定で「KML時点 t において浸水エリア内にある A31a ポリゴン」を閉鎖対象とする

**入力：**
- `GML_DIR/` 以下のGMLファイル
- `KML_DIR/` 以下の8時点KMLファイル

**処理フロー：**
```
1. A31a GML を xml.etree.ElementTree でパース（xlink参照を手動解決）
   → waterDepth >= FLOOD_DEPTH_THRESHOLD のポリゴンを抽出
2. N03行政区域で常総市境界にクリップ（河川コード絞り込みは不要になる）
3. CRS確認 → EPSG:6668
4. KMLファイルをタイムスタンプ順に読み込む（8ファイル）
5. 各KML時点のLineStringを buffer(幅=50m, EPSG:6690で計算) でPolygon化
6. KML全ジオメトリの union_all().convex_hull を浸水エンベロープとして取得
7. A31aポリゴン × KML凸包エンベロープで intersects 判定（凸包内0件の時点はA31a全体をフォールバック）
8. 時刻 → 浸水ポリゴンGeoDataFrameの辞書を生成
9. pickle で保存 → flood_polygons.pkl
10. foliumで時刻別浸水範囲を可視化 → flood_timeline_map.html
```

**出力：**

| ファイル | 形式 | 内容 |
|---------|------|------|
| `output/flood/flood_polygons.pkl` | pickle | `dict[str, GeoDataFrame]` タイムスタンプ→浸水ポリゴン |
| `output/flood/flood_timeline_map.html` | HTML | 時刻別浸水範囲の可視化 |

**主要関数シグネチャ：**
```python
def load_a31a_gml(gml_dir: str) -> gpd.GeoDataFrame
def load_kml_timeline(kml_dir: str) -> dict[str, gpd.GeoDataFrame]
```

### 5-5. i3_route_search.py

**目的：** 250mメッシュ重心（浸水エリア内）から最寄り避難所へのDijkstra最短経路を、各時点の封鎖状況を反映しながら計算する。逃げ遅れエージェント（到達不可）をカウントする。

**入力：**
- `output/network/joso_road_network.graphml`
- `output/closure/road_closure_timeline.json`
- `MESH_FILE`（T001178）
- `SHELTER_DBF`（P20）

**処理フロー：**
```
1. 出発地（origin_points）の生成：
   a. T001178 を Shift-JIS で読み込み
   b. KEY_CODE先頭6桁が 543907 または 543917 のメッシュを抽出
   c. 各メッシュのBounding Boxから重心座標を計算
   d. A31a浸水ポリゴンと重ね合わせて浸水エリア内メッシュのみ残す
   e. origin_points.csv として保存

2. 避難所（destinations）の整備：
   a. P20 DBFを geopandas で読み込む
   b. P20_001="08211" かつ P20_007="1" を抽出（19件）
   c. CRS変換 EPSG:4612 → EPSG:4326
   d. shelters.csv として保存

3. 各時点の経路計算：
   a. GraphMLからグラフGを読み込む
   b. 各出発地から最近傍ノードを取得（ox.distance.nearest_nodes）
   c. 各避難所から最近傍ノードを取得
   d. 各時点の閉鎖エッジ（必要に応じて累積閉鎖）をGから除いたサブグラフを生成
   e. networkx.shortest_path(weight='length') でDijkstra経路計算
   f. 経路なし（NetworkXNoPath）のエージェントを記録

4. 出力ファイルを保存
5. foliumで時点別ルートを可視化
```

**出力ファイル：**

|---------|------|
| `output/agents/origin_points.csv` | 出発地（KEY_CODE, lon, lat, total_pop, elderly_pop） |

## 9. CRS管理方針

| 処理段階 | 使用CRS |
|---------|---------|
| A31a GML読み込み | EPSG:6668（ソースのまま） |
| KML読み込み | EPSG:4326 → EPSG:6668に変換 |
| P20 DBF読み込み | EPSG:4612 → EPSG:6668に変換 |
| 空間演算（sjoin, intersects） | **EPSG:6668で統一** |
| osmnx グラフ | EPSG:4326 → gdf変換後EPSG:6668 |
| folium可視化用出力 | EPSG:4326に戻す |

**原則：** 空間演算の直前に全レイヤーを `to_crs("EPSG:6668")` で統一し、`assert gdf.crs.to_epsg() == 6668` で確認する。

## 10. エラー処理方針

| ケース | 対応 |
|--------|------|
| KMLが読み込めない（driver未対応） | `pyogrio.supported_drivers` 確認、`LIBKML` または `KML` を明示指定 |
| GML読み込み失敗 | `pyogrio.listlayers()` でレイヤー名確認後に `layer=` 指定 |
| 経路が存在しない（孤立ノード） | `try/except nx.NetworkXNoPath` で捕捉し unreachable に記録 |
| メッシュの座標変換エラー | KEY_CODEから座標を逆算する関数で対処（JIS X 0410準拠） |
| osmnxの取得失敗（ネットワーク不通） | GraphMLキャッシュが存在する場合はキャッシュから読み込む |
