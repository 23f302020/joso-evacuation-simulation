## 2. 残存する欠陥（重大度順）

### 【HIGH】`traci.close(False)` によるハッシュ競合とA/B非対称（夜1のB計測run前に必須）

- **箇所**：`04_プログラム/scripts/p2_traci_bus.py:689` が `traci.close(False)`。A側は `04_プログラム/scripts/p2_region_pipeline.py:1658` で `traci.close()`（終了を待つ）。
- **問題**：`wait=False` はSUMOプロセスの終了を待たない。その直後（`p2_traci_bus.py:866` 付近）で `fcd`・`tripinfo` の sha256 を計算するため、**SUMOがまだ書き込み中のファイルをハッシュしうる**。
- **改訂AC5への影響**：(a) 記録されたハッシュが不完全ファイルのものになり、後日の `sha256sum` 再照合で不一致となる。(b)「fcd閉じタグ完全」の検査を通らない。いずれもAC5「出所単一性」を満たさず、当該runは「出所不明」と判定されてやり直しになる。
- **加えて**：A側は待ち、B側は待たないという**終了処理のA/B非対称**であり、決定1（共通モジュール抽出）が消そうとした欠陥クラスそのもの。
- **修正方針（実装は別作業）**：`traci.close()`（待つ）に変更するか、ハッシュ計算前にSUMOプロセスの終了を明示的に待つ。
- **修正時期**：**最優先。夜1でB計測runを並行させる場合、直さないとB側成果物がAC5照合を通らない。** A' full実行（A側のみ）には影響しない。

> **判断（[[段0是正_方針判断_fable5]] 決定17）**：HIGH判定は妥当と確認。修正＝`traci.close()`（wait=True）への1語変更。finally内のまま。ただし帰結(b)「fcd閉じタグ検査を通らない」は不正確——閉じタグ検査は照合時点に行うため通り得る。信頼できる症状はハッシュ再計算の不一致であり、**閉じタグ検査の通過を出所の証拠としてはならない**。

### 【MEDIUM】A側に `run_manifest` がない

- **箇所**：`p2_region_pipeline.py` に `git_state`・`started_at`・`outputs` の sha256 が存在しない。10pctスモークの `scenario_a_10pct_traci_summary.json` にも `run_manifest` キーがない。
- **問題**：改訂AC5の文言は「全**B**成果物」であるため条文違反ではない。しかし今回生データを失ったのは**A側**であり、R4'は正本runである。
- **修正方針**：`p2_traci_common.py` に既にある `git_state()`・`file_manifest()` をA側から呼ぶ。
- **修正時期**：段0の追補、または段2（B確定run前）。

> **判断（決定18）**：MEDIUMから**夜1前必須**へ格上げ。マニフェストは事後付与できず、A'（正本run）を先に走らせると12h再実行が必要になる。「段0の追補、または段2」は誤り。

### 5.2 BLOCKER機構診断の訂正

Opusは当初、AC5第2改訂の「`git_dirty=false`」を検証する過程で「SUMOのrunがoutput/を汚すため `git_dirty=false` は構造上成立しない」とBLOCKER判定した。**この機構診断は誤りであった**（[[manifest_git_dirty_方針判断_fable5]] 決定24〜30、Opus検証注記で確認）。

- `.gitignore:21` の `04_プログラム/output/sumo/**` により、runが書く `regions/08211/results/` 配下（fcd・tripinfo・summary・各log）はすべてignore済みで、`git status --porcelain` に一切現れない。Opusの「SUMOのrunそれ自体が `output/` 配下に書き込むため、runの終了時点でツリーは必ずdirtyになる」は、この除外規則を見落としていた。
- dirty な output/ 215件はPhase 1の公開用資産であり、run出力ではない。`git diff --ignore-all-space --stat -- 04_プログラム/output/` は3ファイル・184挿入のみ（`faq.html`・`region_derived_summary.csv`・`region_run_summary.csv`）。空白を無視しない場合は215ファイル・28,032挿入・27,893削除。すなわち212件は改行コードのchurnであり、既存の未コミット衛生問題である。
- A側 `upsert_summary(RUN_SUMMARY_CSV, ...)`（`p2_region_pipeline.py:1755`）は `git_state()`（`:1733`）の後に実行される。したがってクリーンツリーからの単発runは現行コードのまま `git_dirty=false` を記録できる。「構造上成立しない」は誤り。

**真の構造矛盾（Opusも見落としていた）**：`04_プログラム/output/sumo/regions/_management/region_run_summary.csv` は `git ls-files --error-unmatch` で**tracked**と確認。`.gitignore` は既にトラック済みのファイルを追跡から外さないため、`output/sumo/**` の除外規則にかかわらずgit管理下に残る。A側runは終了時にこのtracked CSVをupsertする。よって決定15が許可した「A'＋B計測の並行」「S系2run/晩」では、先に終わったrunのupsertが後に終わるrunのマニフェストを必ず汚す。「正本run前に毎回コミット」を義務化してもrun同士の相互汚染は解消しない。AC5第2改訂の `git_dirty=false` は決定15の実行計画と条文レベルで矛盾していた。
