## 2026年5月22日 READMEアップロード時エラー対応

原因は，RAG版 `README.md` のYAML front matterで `colorTo: cyan` を指定していたことである．Hugging Face Spaceで使用できる色に `cyan` は含まれていないため，`colorTo: indigo` へ修正した．

## 2026年5月22日 Space起動後の実行時エラー対応

ユーザーが `app.py`，`README.md`，`requirements.txt` を更新後，Space上の3ファイルはRAG版に反映されていることを確認した．ビルドは進行し，runtimeは `BUILDING` から `APP_STARTING` へ進んだが，最終的に `RUNTIME_ERROR` となった．

Hugging Face APIで確認したエラーは以下である．

```text
ModuleNotFoundError: No module named 'audioop'
ModuleNotFoundError: No module named 'pyaudioop'
```

原因は，Hugging Face SpaceのPython 3.13環境で標準ライブラリ `audioop` が削除されており，Gradioの依存ライブラリ `pydub` が代替の `pyaudioop` も見つけられなかったことである．

対応として，当初 `04_プログラム/chatbot_hf_space/requirements.txt` に以下を追加した．

```text
pyaudioop>=0.2.0
```

しかし，2026年5月24日に確認したところ，`pyaudioop` はpipで取得できず，Spaceのruntimeは `BUILD_ERROR` になっていた．Python 3.13で `audioop` を補う代替パッケージとして `audioop-lts` が存在することを確認し，`requirements.txt` を以下に修正した．

```text
audioop-lts>=0.2.2
```

次に，修正後の `requirements.txt` をSpaceへ再アップロードする必要がある．

## 2026年5月24日 起動時間対策

`huggingface-hub>=0.23.0,<1.0.0` を反映後，Spaceは `BUILDING` から `APP_STARTING`，さらに `RUNNING` まで進んだ．しかし，`/config` 取得は長時間タイムアウトし，ページも `building` 表示のままだった．

原因として，`app.py` がGradio起動前に以下の重い処理をすべて実行していたことが考えられる．

- GitHubリポジトリのclone
- Markdown資料の読み込み
- `intfloat/multilingual-e5-small` の読み込み
- FAISSインデックス構築

対応として，`app.py` を修正し，これらの処理をSpace起動時ではなく初回質問時に実行する方式へ変更した．これにより，Gradio画面自体は先に起動し，初回質問時のみ検索インデックス構築の待ち時間が発生する構成になる．

次に，修正後の `04_プログラム/chatbot_hf_space/app.py` をSpaceへ再アップロードする必要がある．

## 2026年5月24日 Gradio起動設定エラー対応

遅延実行版 `app.py` を反映後，Spaceのruntimeで以下のエラーが発生した．

```text
ValueError: When localhost is not accessible, a shareable link must be created.
TypeError: argument of type 'bool' is not iterable
```

原因は，Hugging Face Spaces上で `demo.launch()` がlocalhost判定に失敗したことと，GradioのAPIスキーマ生成時に型注釈が影響した可能性があることである．

対応として，`04_プログラム/chatbot_hf_space/app.py` を以下の方針で修正した．

- `respond()` の型注釈を外す．
- `send_button.click()` と `question.submit()` に `api_name=False` を指定する．
- `demo.launch()` を `server_name="0.0.0.0"`，`server_port=int(os.getenv("PORT", "7860"))` で起動する．

次に，修正後の `app.py` をSpaceへ再アップロードする必要がある．

## 2026年5月24日 Chatbot TextMessage形式対応

前回修正後，Spaceは `RUNNING` となり，`/config` も取得できたが，API質問実行時に `event: error` となった．

`/config` のChatbotスキーマを確認したところ，`content` は単純な文字列ではなく，以下のようなTextMessage配列である必要があった．

```json
{"role": "assistant", "content": [{"type": "text", "text": "回答本文"}]}
```

対応として，`respond()` の履歴出力を以下の形式へ修正した．

```python
history.append({"role": "user", "content": [{"type": "text", "text": message}]})
history.append({"role": "assistant", "content": [{"type": "text", "text": answer}]})
```

次に，修正後の `app.py` をSpaceへ再アップロードする必要がある．

## 2026年5月24日 Chatbot履歴形式の再修正

Gradio 6.5.1対応Chatbot修正版を反映後，Spaceは `RUNNING` となり，`/config` も取得できた．しかし，API経由で質問を送ると `event: error` となった．

`/config` のChatbot定義を確認したところ，`type` 引数は使えない一方で，Chatbotの値はメッセージ形式を想定している可能性が高かった．そのため，`respond()` の履歴形式をタプル形式から以下の `role/content` 形式へ戻した．

```python
history.append({"role": "user", "content": message})
history.append({"role": "assistant", "content": answer})
```

また，RAG処理中の例外がGradioイベント全体のエラーとして消えないよう，`respond()` 内で例外を捕捉し，チャット本文にエラー内容を表示するよう修正した．

次に，修正後の `app.py` をSpaceへ再アップロードする必要がある．

## 2026年5月24日 Gradio 6.5.1移行

```text
requirements.txt: gradio>=6.5.1,<7
requirements.txt: huggingface-hub>=1.0.0,<2.0.0
```

あわせて，Gradio 6系では元テンプレートと同じく `demo.launch()` のみで起動する構成に戻した．

次に，修正後の `app.py`，`requirements.txt`，`README.md` の3ファイルをSpaceへ再アップロードする必要がある．
