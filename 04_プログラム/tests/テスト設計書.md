## 0. この文書の位置づけ

本研究は、卒論の結論（自家用車避難 vs デマンドバスの避難効率・公平性）が
**約11,000行のPythonパイプラインの出力**に依存する。したがって「コードが正しく
動くこと」より「**結果が再現可能で、主要な計算式が正しいこと**」を保証するテストが要る。

Webサービス的な80%カバレッジ志向は採らない。代わりに、卒論の主張を支える
**3段の関数連鎖**を確実に押さえる：

```
(A) 閉鎖エッジ集合    →  (B) 車両数・エージェント分類  →  (C) 評価指標・公平性
   浸水深0.5m判定          full/10pct/救出車両会計          到着率・逃げ遅れ率・完了時刻
   30mバッファ空間結合      Type1〜4分類                    公平性指標（Phase3で新設）
```

いずれも実コード上で純関数として分離済み、または小改修で分離可能であることを
Fable 5 が確認済み。本書はその設計を実行可能な形にまとめたものである。

## 1. テスト戦略の要約（ROI順）

| 優先度 | 種別 | 対象 | 根拠 |
|--------|------|------|------|
| **最高** | 回帰テスト（golden file） | 評価CSV・GeoDataFrame・閉鎖辞書のスキーマと集計値 | 既存の「手動再実行＋Markdown記録」をそのまま自動化。コード無変更で即導入可 |
| **高** | 単体テスト（純関数） | 浸水深0.5m判定・車両会計・Type1〜4分類・評価指標 | 卒論結論を支える計算式を直接保証 |
| **中** | スモークテスト | 各スクリプトが小規模サンプルで例外なく走るか | 大規模ファイル（2472行等）の破損検知 |
| **中** | 契約テスト | 外部データ取得層の列名・型・CRS | OSM/GIS形式変化・キャッシュ破損の早期検知 |

| **やらない** | 網羅カバレッジ・フルSUMO回帰・HTML E2E | — | コスト過大。締切のある卒論に不適 |

## 2. 重要な設計上の事実（実コード検証済み）

### 2.1 浸水深0.5m閾値は「二重構造」

卒論の道路閉鎖ルール「浸水深0.5m以上で閉鎖」は、コード上**2系統**で表現される。
テストは両方を押さえる必要がある。

| 系統 | 実装箇所 | 閾値の形 | 境界テスト値 |
|------|----------|----------|--------------|
| 浸水ナビ API 経路 | `i1_spatial_join.build_suiboumap_flood_dict`（`depth_m >= threshold_m`） | **float 0.5m** | 0.499 / 0.5 / 0.501 |
| A31a GML 経路（現行既定 `CLOSURE_SOURCE="kml_a31a"`） | `e1_load_flood_data.load_a31a_gml`（`waterDepth >= FLOOD_DEPTH_THRESHOLD`） | **int コード値 2** | 1 / 2 / 3 |

> config 検証済み：`FLOOD_DEPTH_THRESHOLD = 2`、`FLOOD_DEPTH_THRESHOLD_M = 0.5`、
> `CLOSURE_SOURCE = "kml_a31a"`。**現行の本番経路は int コード値2** である点に注意。

### 2.2 重複実装が4組ある（ドリフト事故の最大リスク）

常総市版（`i3` / `p2_derived_data`）と全域版（`p2_region_pipeline`）で同一ロジックが
コピーされている。**片方だけ修正して結果が乖離する事故**を防ぐため、同値性テストを最優先の保険とする。

| 関数 | 実装A | 実装B |
|------|-------|-------|
| `meshcode_to_lon_lat` | i3_route_search.py:41 | p2_region_pipeline.py:759 |
| `full_vehicle_count` | p2_derived_data.py:128 | p2_region_pipeline.py:789 |
| `ten_percent_vehicle_count` | p2_derived_data.py:134 | p2_region_pipeline.py:795 |
| `nearest_edge` | p2_sumo_snap.py:39 | p2_region_pipeline.py:906 |

### 2.3 config スナップショットで「黙って結論が変わる」事故を防ぐ

感度パラメータ（`NON_CAR_RATE=0.15`, `HOUSEHOLD_SIZE=2.3`, `FLOOD_DEPTH_THRESHOLD`,
`BUS_*`, `RESCUE_*`, `SIM_DURATION_H=6` 等）を data_regression で固定。値を変えると
テストが落ちるので、変更が意図的であることを常に確認できる。

## 4. 具体的テストケース（ID・優先度付き）

### T1 浸水深0.5m閾値 — P0 — `tests/unit/test_flood_threshold.py`
- `build_suiboumap_flood_dict`（parametrize, ids=["below_0.499","at_0.5","above_0.501"]）
  - depth=0.499 → 除外（メッシュ0件）／ 0.5 → **採用**（`>=` なので0.5ちょうどは閉鎖）／ 0.501 → 採用
  - depth=0 / None / 欠損ts → 除外
  - 非空時 CRS==EPSG:6668、セル幅=11.25/3600度・高さ=7.5/3600度（rtol 1e-9）
- A31a コード値（ミニGML fixture）：waterDepth=1→除外 / 2→採用 / 3→採用
- `generate_shelters_safety` 危険判定：max_depth code=1→safe、=2→flood_risk=True・is_safe_destination=False

### T2 閉鎖辞書生成 — P0 — `tests/unit/test_closure.py`
- `build_closure_dict`
  - 道路直上の浸水セル → 当該edge_id が閉鎖入り
  - 道路から29m → 閉鎖（30mバッファ内）／ 31m → 非閉鎖（**投影座標で距離を作為したfixture**）
  - 空時刻 → `closure[ts]==[]`、出力はソート済み・重複なし
  - CRS不一致入力（WGS84 flood × JGD2011 edges）→ 自動to_crsで同結果
- `_ensure_edge_id`：u/v/key→`"u_v_key"`、既存列→無変更、**元DataFrame非破壊**
- `build_closure_diagnostics`
  - 単調増加 {t0:[a], t1:[a,b]} → new=[1,1] / lost=[0,0] / cumulative=[1,2]
  - 消失 {t0:[a,b], t1:[b]} → lost_edges>0（閉鎖単調性の裏付け）
- **契約テスト**：`build_closure_dict` の出力edge_id を `make_subgraph` に渡すとエッジが除去される（重複実装ドリフト検出）

### T3 メッシュ変換 — P0 — `tests/unit/test_meshcode.py`
- 既知値照合：`"5439071000"` → (lon=139.8765625, lat=36.009375)、`"5439171000"` → (139.8765625, 36.092708333...) ※`pytest.approx(abs=1e-9)`
- 9桁入力 → zfill(10) 解釈
- 不変条件（hypothesis）：543907/543917帯 → 36<lat<36.3, 139.8<lon<140.2
- **i3版 == region版 の同値性**（重複実装ドリフト検出）

### T4 車両会計 — P0 — `tests/unit/test_vehicle_accounting.py`
- `full_vehicle_count`：0→0, -1→0, 1→1, 2→1, 3→2, 23→10, 100→44
- `ten_percent_vehicle_count`：0→0, 1→1, 10→1, 11→2
- `allocate_integer_counts`
  - raw=[1.4,1.4,1.2], target=4 → sum==4、各値≥floor
  - hypothesis：target≥Σfloor で sum==target
  - **target<Σfloor → floorsのまま（合計超過）を仕様として固定**
- **derived版 == region版 の同値性**

### T5 エージェント4分類 — P0 — `tests/unit/test_agent_types.py`
- `allocate_agent_types`（parametrize）
  - total=100, elderly=27 → type4=round(27×0.15)=4, type2=23, type3=round(73×0.15)=11, type1=62、**総和=100**
  - total=0 → 全0、elderly=total（全員高齢者）
  - elderly>total（データ異常）→ non_elderly=0クランプ。挙動を仕様化 or 異常入力テストとして明示
  - hypothesis（0≤elderly≤total≤2000）：4タイプ合計==total_pop、全値≥0、bus_priority ≤ bus_candidate

### T6 評価指標 — P0 — `tests/unit/test_evaluation.py`
- `ratio`：(0,0)→0.0、(1,3)→0.333333
- `read_bool_series`："True"/"true"/"1"/"yes"→True、"False"/"0"/""/NaN→False
- `summarize_vehicle_log`（tmp_path CSV）
  - 全到着 → completion_time=last_arrival, status="complete"
  - 1台未到着 → completion_time="", status="incomplete"
  - 空CSV・文字列混入 → クラッシュしない
- `summarize_major_route_congestion`：速度空欄行の除外・min/max・全空→""
- stranded_main式（vehicle_rows組み立てを関数抽出後）：真理値表を網羅

### T7 スナップ・経路 — P1 — `tests/unit/test_snap_route.py`
- `nearest_edge`（FakeNet）：距離=500.0→"matched"、500.1→"far"（**FAR_THRESHOLD_M境界**）、候補なし→unmatched
- `compute_route`：近い避難所の経路、全滅→None
- `make_subgraph`：存在しないedge_id無視（仕様固定）
- `find_nearest_node`：同距離タイの決定論性

### T8 I/Oガード — P2 — `tests/unit/test_io_guard.py`
- PermissionError注入（OneDrive環境固有）：既存ファイルあり→False返却＋保持、なし→raise

## 8. 最小限のコード改修（テスト前提整備）

原則スクリプトは無変更。ただし以下2箇所のみ、テスト可能化のため純関数抽出を推奨（P1）：

1. `run_traci_scenario` 内の **stranded_main 判定・vehicle_rows 組み立て**を関数として切り出す（TraCI非依存に）。
2. 同内の **major_route congestion 集計呼び出し**を純関数境界で分離。

いずれも karpathy-guidelines「Surgical Changes」に従い、挙動を変えない最小抽出に留める。
