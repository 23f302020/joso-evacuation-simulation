## 原因別の分岐

| 観測 | 次に調べること |
|---|---|
| 検証・recordが総時間の大部分 | 保存済み原本の読取計測で、CSV解凍・再計算・SHA・書込のどこが支配的か調査。現在の凍結検証器へ変更/プロファイラ注入はしない |
| 確認済みの開始待ちが長い | 誰がどの条件を待っているか特定し、既存の終了補助・通知・担当手順の不足だけ改善。排他・復旧・開始ゲートを維持 |
| 空きメモリ10%未満が5分以上続き、同時にページ出力/入出力負荷と処理速度悪化が見える | 不要アプリ削減等の前後を比較。ページ入力だけでスワップ原因と断定しない。アプリ強制終了・同期停止・増設購入は自動実施しない |
| 単一Pythonが約1論理CPUを使い続け、ディスク待ちやメモリ圧迫が小さい | CPU処理候補を保存済み成果物/隔離fixtureで測る。全体CPUの低さだけで余力ありとしない |
| ディスクqueueが継続し、CPUが低く、読書負荷と進行低下が一致 | 読書工程と同期等の競合を確認。観測削減・原本削除・無許可の出力先移設をしない |
| 通常の1本実行で上記が改善したが、独立計算に余力がある | 初めて2本並列の技術設計を検討。現CLIの1セル制約を解除せず、別途排他/保存容量/復旧/結果一致を検証する |

並列試験に進む場合も、採用基準は検証・正式記録を含む処理件数の改善です。まず同じ人工入力の逐次/2本並列でイベント・会計・距離・最終状態と独立検証の一致を確認します。時刻等の運用metadataまで同じSHAになることは要求しません。
