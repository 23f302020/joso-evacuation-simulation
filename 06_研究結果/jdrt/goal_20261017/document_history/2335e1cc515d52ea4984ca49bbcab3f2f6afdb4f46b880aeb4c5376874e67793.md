# モデル運用基準

> 作成日：2026/07/09  
> 現行運用更新：2026/10/18
> 目的：本研究で使用するAIモデル・エージェントの役割分担を固定し、判断の再現性と記録の一貫性を担保する。

> **適用上の注意：** 現在の運用は§0。§1〜§4はPhase 3当時の分担・判断記録を保全した履歴であり、現在のモデル名・利用可能性・必須引継ぎを規定しない。研究条件変更の判断権限はモデル能力と区別する。

## 0. 現在の適用（現行系列全体）

- 2回以上発生した同種作業は既存スキルへ集約し、既存があれば再利用し、不足だけ拡張する。
- 定型監視・記録など思考負荷が低い作業は`gpt-6-luna low`を第一候補とし、必要品質を保つ範囲でモデルを下げるか試行量を抑える。
- 判断、異常解析、複雑な実装、数式による考察など判断負荷が高い作業は`gpt-6.1-sol high`を使用する。
- 定型記録の担当者は異常を独自に新解釈せず、事実と証跡を記録して判断担当へ戻す。
- モデルの能力と研究方針の承認権限は別であり、未承認の研究条件をモデル判断で変更しない。
- 最新のユーザー指定を優先し、定型はLuna low、判断負荷が高い作業は6.1 Sol highとする。本親chat自身の実設定は変更できない。
- 独立検証は一次成果物から再計算し、別モデルの追認だけで代用しない。

- ユーザーの明示指示により、現在のCodexは事前登録済みJDRT v2の技術実装、1セルずつのrun、独立検証、記録、完了後の既定評価を継続してよい。
- 実行順と記録は`.agents/skills/joso-jdrt-runner/`、現在値は`context.md`、方法と固定値はPAP v2・Parameter Registry v2を正本とする。
- 単一セルの結果を理由にPAPやパラメータを変更しない。
- 新しい方法論判断が必要な場合は、現担当が実測に基づく論点・代替案・影響を整理し、ユーザーの明示判断を得て事前登録する。旧§3の特定モデルへの引継ぎは現在の必須条件ではない。
- モデル名や利用可能性が将来変わっても、役割の原則である「事実確認」「方針判断」「記録」「独立検証」の分離を維持する。

### 能力に基づく運用

- 現担当は調査、設計、新規実装、修正、検証、記録、登録済み分析を一貫して進めてよい。通常作業でモデル交代や段階ごとの承認を要求しない。
- ユーザーの選択モデルと推論設定を維持する。この文書を編集しても実際のモデル設定は切り替わらない。
- モデル選択を依頼された場合、公式ガイドの現在の例ではLunaは範囲の明確な反復作業、GPT-6.1 Solは複雑な技術作業と時間・費用の両立、Astraは曖昧な問題や深い分析に位置付けられる。これは2026-10-09の参照例であり、全製品・アカウントでの利用可能性を保証しない。
- 推論量は同じ代表課題で比較し、必要品質を満たす設定を選ぶ。すべての作業をlow/mediumに固定したり、常に最高設定を求めたりしない。
- 異常時は後続runを止め、SHA・会計・ログ・一次成果物から診断する。現在の担当が扱える技術診断・復旧は進め、未解決の能力不足がある場合に具体的な理由とモデル変更案を提示する。
- 独立検証は生成側の判定だけに依存せず一次成果物から再計算する。別モデルの同意を独立検証の代わりにしない。

### 現在の研究判断と記録

事実確認→選択肢・根拠・不確実性の整理→ユーザーの方針判断→事前登録→実装・検証の順とする。現担当は調査と判断案作成を行えるが、未承認のPAP・比較方式・除外規則を変更しない。既存手順に沿う技術作業は継続する。

判断日、担当（分かる範囲のモデル・推論設定）、ユーザー判断の出典、前提正本、結論、項目別確信度、状態、波及タスクを記録する。数値は実ファイルで検証し、事実・推論・未確定事項を区別する。過去メモのモデル名と保存先は改名しない。

根拠（2026-10-09確認）：[公式モデル選択](https://developers.openai.com/api/docs/guides/model-selection)、[強いモデル向け指示の見直し](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)。具体的な研究承認境界はこのプロジェクトの規則である。

## 3. 研究方針の判断プロセス（3段階分離）

方針判断は必ず次の順で行い、各段階を別モデルが担当する。

```
論点整理（Opus）→ 判断（Fable 5）→ 記録（Sonnet 5 または Opus）
```

| 段階 | 担当 | やること | やらないこと |
|------|------|---------|-------------|
| **論点整理** | Opus | 関連文書・実装・実測値を読み、事実と論点を抽出して判断者に渡す | 結論を出さない |
| **判断** | Fable 5 | 方法論上の決定を下す。提案の追認ではなく批判的検証を行う | ファイルの作成・編集をしない |
| **記録** | Sonnet 5 / Opus | 判断内容を既存書式のメモに書き起こす | 数値を再導出しない・判断を変えない |

### 段階分離の理由

- 論点を整理したモデルがそのまま判断すると、自らの整理の枠内でしか結論が出ない。判断者を分けることで前提そのものを疑える。
- 記録者は判断結果を写すだけに徹する。数値の再導出を許すと、記録段階で判断と食い違う値が混入する。
- **判断の入力となる数値は、記録前に必ず実ファイルで検証する**（判断が誤った数値の上に立っていないことを担保するため）。

### 判断メモの保存先

`開発メモ/方針判断_fable5/{段階フォルダ}/{論点名}_方針判断_fable5.md`

書式は `車両会計_方針判断_fable5.md` に揃える（メタ情報テーブル → 判断 → 根拠 → 確定パラメータ表 → 留意点・未解決 → 波及タスク → 確信度 → 参照）。メタ情報テーブルには必ず「プロセス」欄を設け、担当モデルを明記する。

> **注意：** `開発メモ/` は `.gitignore` 対象のため、判断メモはリモートに残らない（ローカル運用）。

---

## 4. 判断メモに必須の記載事項

| 項目 | 内容 |
|------|------|
| 判断日 | 絶対日付で記す |
| プロセス | 論点整理・判断・記録の担当モデル |
| 前提正本 | 判断が依拠する確定済み文書のパス |
| 結論 | 1〜2文で判断の核心 |
| 確信度 | 項目別に 高／中／低 を付す（総合だけでは不可） |
| 状態 | 方針確定か、実装着手済みか |

確信度を項目別に付すのは、後続タスクが「どの前提から検証すべきか」を判断できるようにするため。
