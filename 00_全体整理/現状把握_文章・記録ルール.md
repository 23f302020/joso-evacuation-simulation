# 現状把握資料の文章・記録ルール

制定：2026-10-22。対象は現状把握のMarkdown・HTMLと、その表示文を作る補助処理です。

## 1. 誰に、何を伝えるか

専門知識やプログラミング経験のない人を読者とします。最初の画面で「何を調べているか」「どこまで進んだか」「まだ分からないこと」「次にすること」が分かるようにします。説明を簡単にしても、研究条件・結果の定義・限界は変えません。

## 2. 文章の書き方

- 説明文は「です・ます」で統一します。見出しや表の短い項目名は体言止めでも構いません。
- 結論や現在地を先に書き、理由と補足を続けます。1文では原則1つのことを伝えます。
- 1文はおおむね60文字を目安とし、100文字を超えたら分割を検討します。これは本資料の編集目安であり、研究上の判定条件ではありません。
- 主語や「が・を・に」などを省略した単語の羅列を避けます。同じ意味には同じ言葉を使います。
- 一般的な日本語で表せる内部用語・略語は、本文で使いません。専門語が必要なら、初出で意味を説明します。
- 正確な識別番号・ファイル名・コマンドは、照合用の補足や参照先に残します。URL、記録マーカー、元データの項目名を一括置換しません。
- 「未確認」「この条件に限る」「取得できていない」を省かず、確認できた事実と推測を分けます。未取得の値を0と書きません。
- 数値には対象、単位、全体数、確認時点を添えます。実験内の時間と、パソコンでの処理時間を区別します。

## 3. 記録の単位と状態

経過は日付ごとに、原則「進んだこと → 分かったこと → 残ること・次の作業」の順で短く記録します。1つの箇条書きは1つの話題とします。問題が起きた日は、現象・結果を使えるか・次の確認を書きます。

| 表示する状態 | 意味 |
|---|---|
| 実行中 | 実験の計算を進めています。確認時刻を添えます。 |
| 計算終了・確認中 | 計算は終わりました。結果を採用できるかは未確定です。 |
| 確認・正式記録済み | 元の結果から必要項目を確認し、所定の記録への反映も完了しています。 |
| 問題により停止 | 確認が必要な問題があり、次の実験へ進めません。 |
| 未取得・未確認 | 必要な資料や確認がまだそろっていません。 |

「試験に合格」「計算終了」「研究結果として採用」を混同しません。実行記録と動作状況が食い違うときは、状態の確認が必要と書きます。監視や表示の更新は正式採用を行いません。

## 4. 本文の用語

| 内部の言葉 | 読者向けの表現・説明 |
|---|---|
| JDRT | 予約に応じて車両を配車する避難支援。内部名称は補足で示します。 |
| 静的分析 | ある時点の道路状態を固定して、避難所まで道がつながるか調べる方法 |
| 動的シミュレーション | 時間とともに人や車を動かし、混雑や道路閉鎖の影響を調べる計算 |
| セル | 実験1回分 |
| seed | 動き方のばらつきを再現するための設定番号 |
| validate PASS | 決められた確認項目をすべて通過。何を確認したかも示します。 |
| record7 | 関連する記録への反映を完了。反映前は正式記録済みとしません。 |
| core | 本実験 |
| gate / preflight | 開始や採用に必要な確認条件／開始前の確認 |
| manifest | 実験の設定・開始終了・保存ファイルをまとめた記録 |
| SHA照合 | ファイルが変更されていないことの確認 |
| teleport | 計算上の強制移動。通常の移動と区別して扱います。 |

条件番号だけでは意味が伝わらないため、分かる範囲で説明名を添えます。系列が異なる同名条件をまとめず、意味が未確認なら推測で名称を付けません。

## 5. MarkdownとHTMLの役割

- 説明文と日付別記録はMarkdownを先に更新します。HTMLは同じ内容を読みやすく示します。
- 日付別記録は既存の`PROGRESS_LOG_BEGIN/END`内に、`### YYYY-MM-DD`と`- `で書きます。正式記録マーカーは保持します。
- `status_progress.py --apply`で日付別記録だけをHTMLへ反映し、`--check`で一致を確かめます。HTML全体の再生成や`gen_index.py`は使いません。
- 現在状況は`choice_sync_status.py`で確認した実験回数・状態から更新します。一般読者向けの説明と担当者向けの詳細を分けます。
- 固定された正式記録処理が追加する照合行は、そのまま保持してよい例外です。次の状況表示の同期で平易な表現へ整えます。正式記録処理そのものは変更しません。
- 今回以前の長い技術記録は[改訂前の記録](現状把握_技術記録_20261022.md)へ保全します。改訂後の本文は、研究の説明と短い経過を中心とします。過去の失敗・未確認事項を削除して成功扱いにしません。
- 最新状況、重要な限界、次に必要な確認は常時表示します。過去の日付や技術的な補足だけを折りたたみます。
- 詳細な変更理由・検証・制約はタスクと履歴へ残し、GitHubへ送る際はコミット本文にも記載します。ローカルの修正は公開の許可を意味しません。

## 6. デザインと確認方法

別チャットでの内容更新も、[デザイン維持・更新ガイド](現状把握_デザイン維持・更新ガイド.md)に従い、現在のHTMLの見た目と操作を維持します。通常の記録・説明更新ではCSSや操作用JavaScriptを変更しません。

デジタル庁デザインシステムの文字組、配色の役割、見出し、表、更新履歴の開閉を参考にします。本文は16px以上、行間は文字サイズの1.5倍以上を基本とし、本ページでは18px・1.75倍を採用します。状態は色だけで伝えず、文字で示します。キーボード操作時の選択位置を見えるようにします。

確認ではPC・スマートフォンの幅で、冒頭だけで現在地が読めること、横にはみ出さないこと、日付別記録を開閉できることを確かめます。数値の単位・対象、リンク、正式記録マーカー、MarkdownとHTMLの経過の一致も確認します。非専門者による実際の理解確認は、機械的な文章チェックとは別です。

- [SmartHRの文章指針](https://smarthr.design/products/contents/writing-style/)：内部用語を避け、助詞を省略せず、言葉を統一する考え方を参考にします。
