### 3.1 現在のJDRTでバスはどのように動くか

本資料では、JDRT車両を「予約に応じて配車する避難車両」と呼ぶ。

```text
避難予約が入る
    ↓
60秒ごとに、次に迎えに行く予約を選ぶ
    ↓
車両が予約地点へ移動する
    ↓
乗車に300秒かける
    ↓
指定された避難所へ直行する
    ↓
降車に300秒かけ、次の予約を選ぶ
```

1台が複数の予約地点を回って同時に乗せる相乗りは行わない。1件を迎え、避難所へ送り終えてから次の予約を選ぶ。

## 4. 静的分析の比較内容

### 4.1 静的分析とは

静的分析は、ある時点の道路状態を写真のように固定し、その時点から出発した場合に避難所まで経路があるかを調べる方法である。

静的分析では、次の要素を扱わない。

- 渋滞
- 信号待ち
- 車両同士や歩行者との影響
- 出発後に道路閉鎖が進む時間変化
- 閉鎖発生時の車両の現在位置

### 4.2 静的分析でそろえた条件

Scenario Cの静的分析と動的シミュレーションは、結果を同じにするのではなく、入力条件をそろえて違いを説明できるようにした。

|---|---|
| 対象地域 | 常総市 |
| 出発地域 | 250m単位の405地点 |
| 対象人口 | 21,539人 |
| 車を持たない人の割合 | 10%、15%、20%の3条件 |
| 避難所 | 安全確認済み9施設 |
| 道路 | 動的シミュレーションと同じ道路データ |

| 道路閉鎖 | t0〜t7の8時点 |
| 徒歩距離上限 | 出発地点から道路までの接続距離を含め2km |

| 比較軸 | 条件 | 確認すること |
|---|---|---|
| 時間 | t0〜t7の8時点 | 浸水と道路閉鎖が進むにつれて経路がどう変わるか |

| 徒歩時の浸水 | 厳格条件／浅い浸水を低速で通る条件 | 浅い浸水を通行不可にする場合と、速度を落として通る場合の違い |

### 4.5 静的分析と動的分析の違い

| 項目 | 静的分析 | 動的分析 |
|---|---|---|
| 時間 | 各時点を別々に計算 | 0秒から6時間を連続して進める |
| 経路 | その時点で通れる経路を探索 | 走行中に閉鎖されたら現在位置から迂回する |
| 渋滞・信号 | 含まない | 含む |
| 車・徒歩の相互作用 | 含まない | 含む |
| 主な意味 | 経路が物理的に残る可能性 | 設定した交通条件で実際に到着できるか |

静的な到達可能数と動的な避難完了数は、優劣や精度を直接比較する数値ではない。静的分析は道路構造上の可能性、動的分析は時間と混雑を含む結果として組み合わせて読む。

## 5. 動的データの設計と構造

### 5.1 全体構造

```text
固定入力
  人口・予約・車両・避難所・道路・実際の閉鎖時刻
        ↓
交通シミュレーション
  自家用車と避難車両を0.5秒ずつ動かす
        ↓
運行判断
  1秒ごとに状態を更新し、60秒ごとに配車を判断する
        ↓
時間変化
  車両位置・速度・渋滞・待ち時間・道路閉鎖が変化する
        ↓
結果保存
  人物・予約・車両・混雑・閉鎖・異常・ファイル整合性
```

### 5.2 データの役割

| データ層 | 内容 | 主な役割 |
|---|---|---|
| 人物 | 対象者、支援の必要度、最終状態 | 誰が避難できたかを人物単位で確認する |
| 予約 | 人数、乗車地点、避難先、待ち時間 | 配車先を決め、予約が完了したか確認する |
| 避難車両 | 現在位置、定員、乗車状態、走行距離 | 5台がどのように運行したか確認する |
| 自家用車 | 8,164台の出発・走行・到着 | 避難車両が走る道路の混雑を作る |
| 道路 | 車両位置、速度、旅行時間、閉鎖状態 | 経路探索、迂回、混雑把握に使う |
| 実際の閉鎖情報 | 本当に道路を閉鎖する時刻 | 全方式に同じ現実側の条件を与える |
| 配車用の予測情報 | 配車側に知らせる閉鎖予測 | 方式ごとに情報の有無・正確さを変える |
| 実行記録 | 開始・終了、設定、入力、出力、異常 | 後から同じ条件を確認し、結果の取り違えを防ぐ |

### 5.3 実際の閉鎖情報と予測情報を分ける理由

道路を実際に閉じる時刻と、配車担当が知っている予測時刻は別に管理する。

```text
実際の閉鎖時刻 ──→ 道路を本当に閉鎖する

配車用の予測時刻 ─→ どの予約を選ぶか判断する
```

これにより、予測を使わない方式が将来の正解を誤って利用することを防ぐ。

## 9. 周辺道路の混雑状況はどこまで出せるか

### 9.1 現在のJDRT結果から出せるもの

現在のJDRTでは、60秒ごとに次の3項目を記録している。

- 道路上で走行中の車両数
- ネットワーク全体の平均速度
- 停止している車両数（速度0.1m/s以下）

このため、「何時ごろ全体の混雑が強まったか」は時系列グラフにできる。

### 9.2 現在のJDRT結果だけでは直接出せないもの

JDRTの現行混雑ファイルには、道路区間IDや道路名が入っていない。そのため、現在の出力だけから「避難所周辺のどの道路が混雑したか」を地図へ直接表示することはできない。

| 確認したい内容 | 現在の可否 | 必要な対応 |
|---|---|---|
| 全体の平均速度・停止台数の時間変化 | 可能 | 現行結果をグラフ化する |
| 道路閉鎖時点の迂回成功・失敗 | 可能 | 現行の閉鎖記録を表にする |
| 道路区間ごとの速度・停止・滞留 | JDRTでは未取得 | 道路区間別の観測出力を追加する |
| 避難所周辺の混雑地図 | JDRTでは未作成 | 「周辺」の範囲を決め、道路区間別データを地図化する |
| 配車方式別の周辺道路比較 | 道路区間別の観測不足で未作成 | 全20回完了済みでも道路別混雑は復元できない。追加取得は新系列の観測設計を固定してから行う |

車のみの既存3回については、車両位置データから道路区間別の速度・停止・滞留を再集計済みである。ただし、これは現在のJDRT v2とは別の実験であり、そのままJDRTの道路別混雑結果として扱わない。

### 9.3 Driveのデータ分析資料との対応

Driveの「データ分析」フォルダは読み取りだけで確認した。収集・比較・台帳管理の方法論を示す資料であり、JDRT v2の実測データ本体は入っていない。Drive資料の存在だけを根拠に取得完了とせず、ローカルの一次成果物の列・会計・SHAに照らして判定する。取得済み項目と不足項目の詳細は[データ取得監査](../06_研究結果/jdrt/JDRT-v2_データ取得監査.md)に記録する。

候補別Feasibility Gateの拒否数・理由は既存eventsに未収録で、最終未完了理由から代用できない。全車両の道路区間別軌跡も未保存のため、実際の閉鎖後進入は直接検証できない。teleport 0や閉鎖適用ログを「閉鎖後進入0」と読み替えず、PAPの全項目取得完了とはしない。

### 9.4 周辺道路を表示する前に決めること

「周辺道路」が何を指すかを先に固定する必要がある。

1. 避難所から一定距離以内の道路
2. 避難車両が実際に通った道路
3. 道路閉鎖地点の前後にある道路
4. 平均速度や停止台数が一定基準を超えた道路

この定義を後から結果に合わせて変更すると比較が不公平になるため、道路別の追加取得前に決める。
