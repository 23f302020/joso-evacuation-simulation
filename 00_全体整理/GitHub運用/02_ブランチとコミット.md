# 02 ブランチとコミット

---

## 1. ブランチ構成

| ブランチ | 役割 |
|---|---|
| `master` | 既定ブランチ。GitHub上の「最新の公開版」。Pagesのデプロイ元 |
| `codex/update-latest-research-results` | 現行の作業ブランチ。日常のコミットはここに積む |
| その他（`codex/implement-coding-based-on-documentation*`・`feature/phase1-step1ab`） | 過去の作業ブランチ。履歴として残す。削除はユーザー判断 |

### 運用方針（2026-11-06決定）

**作業ブランチで作業し、同期時に`master`へfast-forwardする。**

- `master`へ直接コミットしない。
- `master`の更新は**fast-forwardのみ**。作業ブランチが`master`を祖先に持たない場合は止まってユーザーに相談する。
- force push（`--force`・`--force-with-lease`）、`rebase`による公開済み履歴の書換え、`reset --hard`での巻き戻しをしない。
- 新しい作業ブランチを作る場合は`<用途>/<内容>`形式（例：`docs/github-guide`）とし、作業後に`master`へFFする。

## 2. コミットの単位

- 1コミット＝1つのまとまった変更。研究run結果の記録と無関係な文書修正を混ぜない。
- 無関係な既存の差分（他の作業中の変更）を巻き込まない。`git add <path>`で対象を明示し、`git add -A`・`git add .`は差分を確認してからに限る。
- 研究runの実行中は、`04_プログラム/scripts/`と入力設定の変更をコミットしない（`CLAUDE.md`）。

## 3. コミットメッセージ書式

```text
<type>: <日本語の要約（1行、句点なし）>

<本文：何を・なぜ変えたか。経過報告の詳細はここに残す>
<検証：何を確認したか。確認していないことも書く>
<公開範囲：載せた／除外したもの。Pages・Cloudflareへの影響>

<エージェントがコミットする場合は、そのツール規定の Co-Authored-By 行>
```

| type | 用途 |
|---|---|
| `feat` | 新しい機能・スクリプト |
| `fix` | 不具合修正 |
| `refactor` | 挙動を変えない整理 |
| `docs` | 文書・記録の追加・更新 |
| `test` | テストの追加・修正 |
| `chore` | 設定・除外・保全などの雑務 |
| `perf` | 性能改善 |
| `ci` | GitHub Actions等 |

### 本文に書くこと

`CLAUDE.md`の規定により、**経過報告の詳細はコミット本文に残す**。本文には次を含める。

- 変更の目的と背景（ユーザー指示があれば要旨）
- 研究条件・指標・採用基準を変えたか（変えていなければ「変更なし」と明記）
- 検証内容と範囲（実施していない検証を実施したように書かない）
- 公開範囲の扱い、Pages／Cloudflareへの影響
- 撤回済み数値・方向主張を書かない（`CLAUDE.md`恒久禁止事項）
- トークン・APIキー・個人情報を書かない

## 4. masterへの反映

作業ブランチをpushする際、同時に`master`もFFで更新する。手順は[03_push手順 §4](03_push手順.md#4-実行コマンド)。

- `--atomic`で作業ブランチと`master`を同時に更新し、片方だけ更新された状態を作らない。
- `master`の更新で`04_プログラム/output/**`に差分があると**Pagesが本番デプロイされる**。push前にユーザーへその旨を伝える。
- ローカルの`master`が古い場合は、チェックアウトせずに`git fetch origin master:master`でFFする。

## 5. PRについて

個人研究のため、通常はPRを作らずFFで反映する。差分を第三者に見せたい・レビューを残したいときだけ、ユーザー判断でPRを作る。
