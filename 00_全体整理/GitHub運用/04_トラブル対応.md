# 04 トラブル対応

> 原則：**履歴を書き換えて解決しない。** 判断に迷ったら止まり、状況をユーザーに報告する。

---

## push が 403 で拒否される

- 原因の多くは`JI-life`の資格情報が使われていること（2026-10-20に実例あり）。
- [03_push手順 §4](03_push手順.md#4-実行コマンド)のとおり、`GH_TOKEN`に`23f302020`のトークンを入れ、`-c credential.helper= -c "credential.helper=!gh auth git-credential"`を付けて再実行する。
- `gh auth switch`で解決しない（`JI-life`に触れない方針）。

## non-fast-forward で拒否される

- GitHub側に、ローカルにないコミットがある。
- `git fetch origin`のあと`git log --oneline HEAD..origin/<branch>`で内容を確認する。
- 自分の作業ブランチなら`git merge origin/<branch>`で取り込み、競合があれば解消してからpushする。
- `master`へのFFが拒否された場合は、作業ブランチに`origin/master`を取り込んでから再度FFする。**force pushはしない。**

## ローカルの `master` が古い

```powershell
git fetch origin master:master   # master をチェックアウトしていないときだけ使える（FFのみ）
```

## 大容量ファイルで拒否される（100MB超）

- まだpushしていなければ、そのコミットからファイルを外して作り直す（`git rm --cached <path>`→`.gitignore`へ追加→コミット）。
- 過去のコミットに入ってしまった場合は履歴の書換えが必要になる。**自分で実施せず、ユーザーに報告して判断を仰ぐ。**

## 秘密情報・除外対象をpushしてしまった

1. すぐユーザーに報告する。
2. 秘密情報なら、**まず該当のキー・トークンを無効化・再発行する**（public リポジトリでは削除しても複製が残る前提で扱う）。
3. 最新版から削除するコミットを作る（`git rm --cached`＋`.gitignore`）。
4. 履歴からの完全削除（`git filter-repo`等）とforce pushは、ユーザーの明示判断があるときだけ。

## Pages のデプロイが失敗した

- Actionsのログを確認する（`gh run view <id> --log-failed`、`GH_TOKEN`は`23f302020`）。
- 研究ファイルを直してから再pushするか、`workflow_dispatch`で再実行する。再実行もユーザーに伝えてから行う。

## 意図しないファイルがステージされた

```powershell
git restore --staged <path>   # ステージから外すだけ（作業ツリーは変えない）
```

`git restore <path>`（`--staged`なし）や`git checkout -- <path>`は作業ツリーを書き換えるので使わない。

## 改行コードの差分が大量に出た

- `core.autocrlf`や`.gitattributes`を変更していないか確認する。
- `output/`の確定物はCRLF/SHAを保全しているため、**戻すためにcheckout/restoreをしない。** 原因を特定してユーザーに報告する。
